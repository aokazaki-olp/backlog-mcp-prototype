# 根D — schema が静的で、起動時に確定する事実を受け取れない

**閉じる指摘**: L3-1（H）、L3-7（M）
**段階**: **5 完了**（2026-09-07）

---

## 段階1 — 理解

```
症状（指摘の言葉）      許可プロジェクトキーを LLM が知る手段が無い／priority・resolution に enum が無い
不変条件（直す対象）    起動時に確定している事実は、tools/list に現れる
```

裏返すと**枝が数えられる**。「schema に載せうる起動時の事実」を全部並べると5つある。

| #   | 事実                                                           | いまの schema                                | 判定                                                                      |
| --- | -------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------- |
| 1   | 添付が使えるか（`BACKLOG_DOWNLOADS_DIR`）                      | **既に反映済み**（`withoutFileProperty`）    | **錨**                                                                    |
| 2   | ツールごとの許可プロジェクトキー                               | 無い（`{ type: 'string', description: … }`） | **L3-1**                                                                  |
| 3   | `priority` / `resolution` の名前集合（スペース共通）           | 無い                                         | **L3-7**                                                                  |
| 4   | `status` / `issueType` / `category` / `milestone` / `assignee` | 無い                                         | **表現できない**（プロジェクトごとに違う。`list_project_masters` の仕事） |
| 5   | 件数の上限（`DEFAULT_LIMITS.maxCount` = 20）                   | 無い（説明文だけ）                           | **起動時の事実ではなく定数**。隣接するが別                                |

**症状の言葉では2つしか見えないが、枝は5つある。** 4 と 5 を混ぜないことが方針を決める。

## 段階2 — 調査（接地）

### 錨はコードの中にある — 新概念は要らない

`toDefinition` は**すでに起動時の事実で schema を変えている**。

```ts
const toDefinition = (toolName: ToolName, attachable: boolean): ToolDefinition => {
  const schema = INPUT_SCHEMAS[toolName];
  return { …, inputSchema: attachable ? schema : withoutFileProperty(schema), … };
};
```

**やることは「静的な schema を動的にする」ではなく、既にある形の一般化**（`指摘をコードで直す` 手順4）。

さらに、**ツールごとの許可キーを返す関数も既にある**。

```ts
export const projectKeysFor = (policy: ResolvedPolicy, toolName: ToolName): readonly string[]
```

いまは `scopedProjectIds`（絞り込みの `projectId` を決める）でしか使っていない。

### 設計文書の側にも根拠がある

`DESIGN.md:109` は正規形の利点として**「`tools/list` とハンドラが同じ集合を参照するのでズレようがない」**と書いている。
いまその原則が効いているのは「**どのツールを載せるか**」だけで、「**どのプロジェクトキーを渡せるか**」には効いていない。
**同じ原則の適用漏れ**であって、新しい主張を持ち込む必要がない。

### L3-1 は実物で確認した — 発見の経路が本当に無い

- `instructions`（`server.ts:41`）は「**対象プロジェクトはサーバ側で決まっており、引数で広げることはできません**」と
  書くだけで、**許可キーを名指ししていない**
- キーを列挙するツールが無い（`list_project_masters` は `projectKey` を**要求する**側）
- 外すと `ScopeDeniedError`（`プロジェクト X では … を実行できません`）が返るが、
  **正解の集合は分からない**。総当たりするしかない

### enum が空にならないことの保証

`listedTools(policy)` は「**どこかのプロジェクトで許可されたツール**」の集合（`policy.ts:233`）。
したがって **`tools/list` に載るツールは、必ず1つ以上のプロジェクトで許可されている** →
`projectKeysFor` は空にならない。**空の `enum` を書く経路が構造上できない。**

### 仕様（2026-09-07 確認・ミラー）

| 出典                         | 内容                                                            |
| ---------------------------- | --------------------------------------------------------------- |
| `server/tools.md` Tool       | `inputSchema` は JSON Schema。**`$schema` が無ければ 2020-12**  |
| `basic.md` JSON Schema Usage | 実装は **2020-12 を必ず支持する**。2020-12 の使用が RECOMMENDED |

`enum` は 2020-12 の標準語彙なので、**仕様上の障害は無い**。

### 横断探索

**種類**: 「**起動時に確定していて、しかも `tools/list` の生成に既に使われている事実が、schema に現れない**」。
`src/` で洗った結果が段階1 の表で、新しい箇所は出なかった。4 は表現不能、5 は定数（別種）。

### 変更する一文の役割

| 変える一文                                    | 何を主張するか                | 何を運ぶか                                              | 誰が寄りかかるか                              |

`toDefinition` は非公開で、呼ぶのは `buildHandlers` の1箇所。
`ToolContext` は **`policy` も `masters` も既に持っている**ので、**新しい依存を足さずに済む**。

| テスト                                                             | 何を固定                                         | 予測                                                      |

## 段階4 — 修正方針（**確認待ち**）

### 1. 何を変えるか

| 変更                  | 中身                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------- |
| `toDefinition` の引数 | `(toolName, attachable)` → **runtime fact をまとめて受け取る形**（`attachable` ＋ `policy` ＋ `masters`）  |
| **L3-1**              | `projectKey` プロパティに `enum: projectKeysFor(policy, toolName)` を足す                                  |
| **L3-7**              | `priority` に `enum: [...masters.priorityIds.keys()]`、`resolution` に `[...masters.resolutionIds.keys()]` |

`INPUT_SCHEMAS` は**静的なまま残す**（雛形）。**差し込むのは `toDefinition` の中だけ**にする。
`withoutFileProperty` と同じ「雛形 → runtime fact で加工」の形を守る。

### 2. どの指摘が閉じるか

- **L3-1**（H）— 許可プロジェクトキーが `tools/list` に出る
- **L3-7**（M）— `priority` / `resolution` に `enum` が付く

### 3. 変更しないと決めた箇所（名指しで外す）

- **`status` / `issueType` / `category` / `milestone` / `assignee`** — **プロジェクトごとに違う**ので
  ツール単位の schema では表せない。`list_project_masters` が担う面であり、**根D の範囲外**
- **件数の上限（`maxCount`）** — `DEFAULT_LIMITS` は定数で、起動時に決まる事実ではない。
  しかも `maximum` を書くと**クライアント側で弾かれる**ようになり、いまの「サーバが切り下げて
  打ち切りを申告する」（規約 §5.4）と挙動が変わる。**別件として外す**
- **`instructions` に許可キーを列挙する案** — schema に載せれば足りる。二重に持つと乖離する

### 4. 段階2 で下した分類

`enum` の追加は**「書くべき」**。無いと LLM は総当たりするしかなく、
`ScopeDeniedError` を返す回数が増える（＝監査ログが拒否で埋まる）。

### 5. 検証の設計

| 種類             | 内容                                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 赤になるはず     | `projectKey` に `enum` が入る／`priority` `resolution` に `enum` が入る                                                                                                  |
| 緑のまま（境界） | **ツールごとに違う集合が入る**（`comment` しか許していないプロジェクトは書き込みツールの enum に出ない）／`status` 等には enum が**入らない**／`file` の有無は変わらない |
| 違反プローブ     | `enum` を落とす・**ポリシーに無いキーを混ぜる**と赤になることを確かめる                                                                                                  |

### 6. 確認したいこと

1. **ポリシーの許可キーを `tools/list` に載せてよいか**（露出の是非）
2. `enum` で閉じるか、`description` に列挙するだけにするか（**`enum` を推す** — クライアントが検証でき、モデルにも閉じた集合として見える）
3. 件数の上限（`maximum`）を**外す**判断でよいか

## 段階4 の続き — プロジェクト名（**人間の指摘で範囲が変わった**）

**「プロジェクトキーはプロジェクト名と一緒に渡さないとだめでは」**という指摘を受け、調べ直した。

- `masters.projectIds` は `projectKey → projectId` **だけ**で、**名前は `isBacklogProject` の時点で捨てている**
- `GET /projects` の応答には `name` がある（ミラーで確認）
- **キーだけでは LLM が選べない** — 「営業の課題を探して」に対して `SALES` を選ぶ手段が無い

### 名前の信頼分類（根B と同じ手順）

| 出典                                                 | 実行可能な権限                              |
| ---------------------------------------------------- | ------------------------------------------- |
| ミラー `update-project.md`（`fetched: 2026-08-30`）  | **管理者 / プロジェクト管理者**             |
| **ライブ**（`developer.nulab.com`・2026-09-07・200） | **管理者 / プロジェクト管理者**（完全一致） |
| `add-project.md`                                     | **管理者**                                  |

根B が確定させた軸（ミラーは「管理者」と「すべての権限」を書き分ける）では、
**プロジェクト名は `status` と同じ「管理者定義」側**。**囲まない。**

### 形（裁定: enum ＋ description の対応表）

`enum` は値の配列しか持てない（JSON Schema 2020-12 §6.1.2「The value of this keyword MUST be an array」。
一次情報を 2026-09-07 に取得して確認）。ラベルは持てないので、**検証は `enum`・案内は `description`** に分ける。
**同じ関数が両方を生成する**ので乖離しない。
