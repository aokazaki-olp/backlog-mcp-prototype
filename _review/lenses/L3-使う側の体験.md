## あなたが担当する失敗モード（これだけを見る）

1. **ツール定義（schema）の分かりにくさ** — `src/contract.ts` の `TOOL_SPECS` と `src/tool/tools.ts` が生成する input schema。LLM がどの引数を渡せばいいか判断できるか。description が実装と食い違っていないか。必須/任意の区別、列挙値、フォーマット（`yyyy-MM-dd` など）が schema から読み取れるか。**LLM は description しか読めない**ので、コード中のコメントに書いてあっても伝わりません
2. **ツールの粒度と命名** — `TOOL_NAMES` の名前から何ができるか推測できるか。似た名前のツールの使い分けが description から判断できるか。ツールの数が多すぎて選べなくならないか
3. **エラーメッセージ** — 拒否されたとき、LLM が**次に何をすればいいか**分かるか。「許可されていません」だけで終わっていないか。逆に、拒否理由を詳しく書きすぎて内部構造を教えていないか（ここはトレードオフとして指摘してよい）
4. **応答の形** — 返ってくる JSON が LLM にとって読みやすいか。冗長すぎないか（トークン浪費）、削りすぎて肝心の情報が落ちていないか。**打ち切ったことが応答から分かるか**（黙って切り詰めていないか）
5. **`instructions` の実効性** — `src/server.ts` の `SERVER_INFO.instructions` と `src/tool/untrusted.ts` の囲み。LLM の立場で読んで、実際に従える指示になっているか
6. **MCP 仕様との齟齬** — 仕様が用意している表現手段を使えていない、または仕様の意図と違う使い方をしている箇所
