## 段階3 — 整合性の確認（**未了**）

### 書き出すべきもの（未着手）

**#2（`attach/` の追加）は「足す」修正で、危険度が最も高い。**
表に行を1つ足すと、`attach/` の「知ってよい／知ってはいけない」を**決めなければならない**。
現状を書き写すのではなく、**設計として何が正しいか**を決める必要がある。

- `attach/localFile.ts` は `node:fs/promises` / `node:path` / `node:crypto` / `file-type` を使う
- `tool/tools.ts` は `attach/localFile.ts` から**型だけ** import している（`ReceivedAttachment`）
- `config.ts` は `attach/localFile.ts` から**値** を import している（`isInside` / `resolveAttachmentRoot`）

**`config.ts` → `attach/` の依存は、表のどの層にも属さない。** `config.ts` は表に無い。
つまり**表の欠落は `attach/` だけではない可能性がある** — 段階3で `src/` の全モジュールが
表のどの行に当たるかを対応付ける必要がある（`main.ts` / `server.ts` / `config.ts` も未掲載）。

**#3・#4 は「狭める」修正。** §5 の表から1行を外すと、
**その行が暗黙に与えていた前提**が無いかを確かめる必要がある（補遺の実例3「狭めすぎ」）。
候補: 「read しか無いプロジェクトのぶんまで引くと、使わない呼び出しが起動時に並ぶ」という
**コストの議論**が他所で参照されていないか。

**#1 は「消す」修正だが、例が前提を担っていないか確かめる。**
`DESIGN.md:443-447` は `FormFields` の話をしながら、
**借り物の `ApiClient.splitFormFields` がスカラー配列を弾く**という事実を運んでいる。
この事実は `contract.ts:352-357` と `tools.ts:1121-1124` にも書かれているので**重複だが**、
「複数添付をやるときに上流の修正が要る」という結論の根拠になっている。
§10 の引用ブロック（`DESIGN.md:430-434`）が既に同じことを書いているので、
**落としても前提は残る** — ただし段階3で確認する。
