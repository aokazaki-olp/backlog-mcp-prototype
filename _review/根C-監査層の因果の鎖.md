# 根C — 監査層。3つの欠陥が因果で繋がっている

**閉じる指摘**: L1-3（引き金）→ L1-1（下流）→ L1-2（下流）
**段階**: 2 完了 / 3 未了 → **方針は未確定**
**範囲**: `src/mcp/audit.ts` 194行 ＋ `src/mcp/stdio.ts` 63行

---

## 段階1 — 理解

3件は**別の欠陥**だが、**1つの引き金から連鎖する**。

> **監査ログの書き出しが失敗したとき、その失敗が本体の処理を壊す。**
> 成功した操作が失敗として返り、本来の例外は消え、記述子が二重に閉じられ、
> 最終的に JSON-RPC のループごと止まる。

**当初「L1-1 と L1-3 は同根」「L1-2 と L1-5 は同根」と推論したが、どちらも誤りだった。**
通読して分かったのは、同根ではなく**因果**だということ。

---

## 段階2 — 調査（接地）

### 因果の鎖

```
L1-3（audit.ts:184-192 — record() が try の外にある）
  ├→ 1回の callTool で record() が2回走る
  │    └→ L1-1（audit.ts:75-86 — fdFor が閉じ済み fd を再度 closeSync する）が発火
  └→ 例外が withAudit から再送出される
       └→ L1-2（stdio.ts:39-62 — for await に try が無く、ループごと死ぬ）に到達
```

**`buildHandlers.callTool`（`tools.ts:2472-2478`）は自分で全部 catch している。**

```ts
try {
  const payload = await runTool(context, toolName, isRecord(args) ? args : {});
  return { content: [{ type: 'text', text: JSON.stringify(payload, null, 2) }] };
} catch (e) {
  const message = Error.isError(e) ? e.message : String(e);
  return { content: [{ type: 'text', text: message }], isError: true };
}
```

したがって **`serve` まで例外が届く経路は `withAudit` の再送出しかない。**
L1-3 が唯一の引き金で、L1-1 と L1-2 はその下流。

### L1-3 — `record()` が try の外にある

`audit.ts:184-192`:

```ts
try {
  const result = await handlers.callTool(name, args);
  record(result.isError !== true);   // ← ここが投げると result が捨てられる
  return result;
} catch (e) {
  record(false, { thrown: ... });    // ← ここが投げると throw e に到達しない
  throw e;
}
```

2通りの壊れ方がある。

1. **成功が失敗に化ける。** `handlers.callTool` が成功して `record(true)` が投げると、
   **結果が捨てられて例外になる。** Backlog へのコメント投稿は済んでいるのに「失敗した」と見える
2. **本来の例外が消える。** catch の中の `record(false, ...)` が投げると `e` は `throw e` に
   到達せず、**`cause` にも入らない**。規約 §6.2（情報を落とさない）が成立していない

しかも `multiAuditSink`（`audit.ts:38-44`）はファイルを先に書くので、
**ファイルが失敗すると stderr にも1行も残らない。**

コメントは「握りつぶさない（規約 §5.4）。記録してから元の例外をそのまま投げ直す」と
書いているが、**シンクが投げた場合はその通りに動かない。**

### L1-1 — `fdFor` の状態更新が `openSync` の後ろにある

`audit.ts:75-86`:

```ts
const fdFor = (date: string): number => {
  if (date === openedDate) {
    return fd;
  }
  if (fd !== -1) {
    closeSync(fd);
  } // ← 閉じる
  fd = openSync(join(dir, `audit-${date}.jsonl`), 'a', 0o600); // ← ここが投げると
  openedDate = date; // ← ここまで来ない
  return fd;
};
```

`openSync` が投げると **`fd` は閉じ済みの古い番号のまま、`openedDate` も古い日付のまま**残る。
次に呼ばれると `date !== openedDate` なので、**閉じ済みの fd をもう一度 `closeSync` する。**

その番号がすでに別の用途（got のソケット、添付の `FileHandle`）に再利用されていれば、
**そのファイル／接続が黙って閉じられる。**

**発火条件**: UTC 日付をまたいだ最初のツール呼び出しで出力先を開けないこと
（ディレクトリが消えた・アンマウント・ディスク満杯・Windows でロック・EMFILE）。
**そして2回目の `record()` があること** = L1-3。

L1 は probe で `EBADF: bad file descriptor, close` を再現し、
**監査シンクとは無関係の `marker.txt` の fd が閉じられる**ことも確認している。

### L1-2 — `for await` に try が無い

`stdio.ts:39-62`。`JSON.parse` は try で囲まれているが、
`const response = await handleMessage(message, handlers, serverInfo);` は裸。

例外で `for await` を抜けると、**そのリクエストに応答が返らず、後続の行も一切処理されない。**
`main.ts` はこれを catch して「**起動に失敗しました**」と出す —
セッション中盤の障害なのに起動失敗と表示され、原因を取り違える。

`RPC_ERROR.INTERNAL`（`-32603`）は `protocol.ts:27` に定義されているが、
**`src/` のどこからも参照されていない**（`grep` で確認）。**返す経路が存在しない。**

### 順序が決まる理由

**L1-2 を先に直してはいけない。** ループが死ななくなると、
L1-1 の発火に必要な「1回の callTool で `record()` が2回」という条件は変わらないが、
**L1-1 の症状（無関係の fd が閉じられる）が観測しにくくなる**。
また L1-3 を直すと L1-1 の発火経路が閉じるので、**L1-1 単体の再現テストを先に固定しないと
直したことを確かめられなくなる。**

→ **L1-3 の修正と同時に、L1-1 の再現テストを置く**のが順序上の要点。

### 欠陥の種類（横断で探す対象）

> **「記録する」処理の失敗が、「記録される」処理の成否を変えている。**

DESIGN.md §5 が「ログのフレームワーク」を捨てた理由として
**「監査と診断は要求が正反対」「`LOG_LEVEL=error` で監査が黙って消える経路ができる」**
と書いている。**この文書は「監査が消える」方向を警戒しているが、
「監査の失敗が本体を壊す」方向は扱っていない。**

`src/` 内で同型を探した結果:

- `writeAudit`（`audit.ts:151-153`）は `server.ts` の `startup` / `startup-failed` からも呼ばれる。
  **`createHandlers` の catch 内（`server.ts:160-167`）で `writeAudit` が投げると、
  元の起動失敗の例外が失われる**（L1-3 と同型。起動時なのでプロセスは落ちるが、
  stderr に出る理由が別物になる）
- `stderrAuditSink`（`audit.ts:31-35`）は `process.stderr.write` が投げうる（EPIPE）

**同型が2箇所ある。** 段階3で扱う。

### 修正案の分類

| 分類         | 判定                                                                                                                                                      |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 段階3 — 整合性の確認（**未了**）

### 書き出すべきもの（未着手）

**「監査を書けなければ起動しない」という fail-closed の主張。**
`server.ts` のコメントが「監査に寄りかかった設計が監査なしで動くのは、
防御について嘘をつくことになる（fail-closed）」と書いている。
**これは起動時の話。** 稼働中にシンクが失敗したときの方針は**どこにも書かれていない**。

段階3で決めるべき問い: **稼働中に監査が書けなくなったらどうするのが正しいか。**

- 止める（fail-closed を貫く）→ 現状の L1-2 が事実上これになっているが、
  **意図した設計ではなく事故**であり、しかも「起動に失敗しました」と誤表示する
- 続ける（本体を優先し、監査の失敗は stderr へ）→ 監査の空白ができる
- **どちらを選ぶにせよ、DESIGN.md に書かれていない決定なので、書く対象になる**

**`AuditSink` インターフェースの契約。** `write(line: string): void` は
**投げてよいのか**が型にも TSDoc にも書かれていない。`multiAuditSink` の
「1つが失敗したら起動を続けない（黙って片方だけ書かない）」というコメントは
**起動時の話をしているが、稼働中も同じ実装が走る。**

**`RPC_ERROR.INTERNAL` を使い始めることの波及。**
`tests/server.test.ts` が `handleMessage` の応答形を固定している。
新しいエラー応答を返すと、**「stdout に JSON-RPC 以外を書かない」テスト**（`stdio.ts` の
差し替え可能な `write` はそのために用意されている）との関係を確かめる必要がある。

**根F との関係。** L4-4 が「`withAudit` の例外経路が未テスト」を挙げている。
**根C を直すとこのテストが書けるようになる**ので、根C の段階5でテストも置く。
根F から L4-4 を根C へ移すかは、段階4で決める。
