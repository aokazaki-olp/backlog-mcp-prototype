# 根C — 監査層。3つの欠陥が因果で繋がっている

**閉じる指摘**: L1-3（引き金）→ L1-1（下流）→ L1-2（下流）＋ **L4-4**（根F から移動）
**段階**: **4 完了（2026-09-07・裁定と方針は確定）** / 5 未了
**範囲**: `src/mcp/audit.ts` 194行 ＋ `src/mcp/stdio.ts` 63行 ＋ `src/main.ts` / `src/server.ts` の言い分け

## 段階1 — 理解

3件は**別の欠陥**だが、**1つの引き金から連鎖する**。

> **監査ログの書き出しが失敗したとき、その失敗が本体の処理を壊す。**
> 成功した操作が失敗として返り、本来の例外は消え、記述子が二重に閉じられ、
> 最終的に JSON-RPC のループごと止まる。

**当初「L1-1 と L1-3 は同根」「L1-2 と L1-5 は同根」と推論したが、どちらも誤りだった。**
通読して分かったのは、同根ではなく**因果**だということ。

## 段階2 — 調査（接地）

### 因果の鎖

```
L1-3（audit.ts:184-192 — record() が try の外にある）
  ├→ 1回の callTool で record() が2回走る
  │    └→ L1-1（audit.ts:75-86 — fdFor が閉じ済み fd を再度 closeSync する）が発火
  └→ 例外が withAudit から再送出される
       └→ L1-2（stdio.ts:39-62 — for await に try が無く、ループごと死ぬ）に到達
```

**`buildHandlers.callTool`（`tools.ts:2472-2478`）は自分で全部 catch している。**

```ts
try {
  const payload = await runTool(context, toolName, isRecord(args) ? args : {});
  return { content: [{ type: 'text', text: JSON.stringify(payload, null, 2) }] };
} catch (e) {
  const message = Error.isError(e) ? e.message : String(e);
  return { content: [{ type: 'text', text: message }], isError: true };
}
```

したがって **`handleMessage` の中で起きる例外が `serve` まで届く経路は、`withAudit` の再送出しかない。**

> **訂正（2026-09-06・実装者コメントの異議による）**
>
> 当初ここに「`serve` まで例外が届く経路は `withAudit` の再送出しかない」と書いた。**誤り。**
> `serve` は `handleMessage` の**外**でも投げる。
>
> ```ts
> // stdio.ts:59-61 — try の外にある
> const response = await handleMessage(message, handlers, serverInfo);
> if (response !== null) {
>   channel.write(JSON.stringify(response)); // ← ここ
> }
> ```
>
> `channel.write` の実体は `main.ts:15-17` の `process.stdout.write` で、
> **クライアントが先に落ちていれば EPIPE で投げる。**（統合者が `stdio.ts:58-62` と
> `main.ts:12-18` を開いて確認、2026-09-06）
>
> つまり **L1-2（ループごと死ぬ・「起動に失敗しました」と誤表示する）は L1-3 と独立に発火しうる。**
> 実害は小さい（stdout が壊れている時点でクライアントは居ない）が、
> **「L1-3 を直せば L1-2 は起きない」と読むと取りこぼす。**

L1-3 は L1-1 の唯一の引き金であり、L1-2 の**引き金のひとつ**。順序の結論は変わらない。

### L1-3 — `record()` が try の外にある

`audit.ts:184-192`:

```ts
try {
  const result = await handlers.callTool(name, args);
  record(result.isError !== true);   // ← ここが投げると result が捨てられる
  return result;
} catch (e) {
  record(false, { thrown: ... });    // ← ここが投げると throw e に到達しない
  throw e;
}
```

2通りの壊れ方がある。

1. **成功が失敗に化ける。** `handlers.callTool` が成功して `record(true)` が投げると、
   **結果が捨てられて例外になる。** Backlog へのコメント投稿は済んでいるのに「失敗した」と見える
2. **本来の例外が消える。** catch の中の `record(false, ...)` が投げると `e` は `throw e` に
   到達せず、**`cause` にも入らない**。規約 §6.2（情報を落とさない）が成立していない

しかも `multiAuditSink`（`audit.ts:38-44`）はファイルを先に書くので、
**ファイルが失敗すると stderr にも1行も残らない。**

コメントは「握りつぶさない（規約 §5.4）。記録してから元の例外をそのまま投げ直す」と
書いているが、**シンクが投げた場合はその通りに動かない。**

### L1-1 — `fdFor` の状態更新が `openSync` の後ろにある

`audit.ts:75-86`:

```ts
const fdFor = (date: string): number => {
  if (date === openedDate) {
    return fd;
  }
  if (fd !== -1) {
    closeSync(fd);
  } // ← 閉じる
  fd = openSync(join(dir, `audit-${date}.jsonl`), 'a', 0o600); // ← ここが投げると
  openedDate = date; // ← ここまで来ない
  return fd;
};
```

`openSync` が投げると **`fd` は閉じ済みの古い番号のまま、`openedDate` も古い日付のまま**残る。
次に呼ばれると `date !== openedDate` なので、**閉じ済みの fd をもう一度 `closeSync` する。**

その番号がすでに別の用途（got のソケット、添付の `FileHandle`）に再利用されていれば、
**そのファイル／接続が黙って閉じられる。**

**発火条件**: UTC 日付をまたいだ最初のツール呼び出しで出力先を開けないこと
（ディレクトリが消えた・アンマウント・ディスク満杯・Windows でロック・EMFILE）。
**そして2回目の `record()` があること** = L1-3。

L1 は probe で `EBADF: bad file descriptor, close` を再現し、
**監査シンクとは無関係の `marker.txt` の fd が閉じられる**ことも確認している。

### L1-2 — `for await` に try が無い

`stdio.ts:39-62`。`JSON.parse` は try で囲まれているが、
`const response = await handleMessage(message, handlers, serverInfo);` は裸。

例外で `for await` を抜けると、**そのリクエストに応答が返らず、後続の行も一切処理されない。**
`main.ts` はこれを catch して「**起動に失敗しました**」と出す —
セッション中盤の障害なのに起動失敗と表示され、原因を取り違える。

`RPC_ERROR.INTERNAL`（`-32603`）は `protocol.ts:27` に定義されているが、
**`src/` のどこからも参照されていない**（`grep` で確認）。**返す経路が存在しない。**

### 順序が決まる理由

**L1-2 を先に直してはいけない。** ループが死ななくなると、
L1-1 の発火に必要な「1回の callTool で `record()` が2回」という条件は変わらないが、
**L1-1 の症状（無関係の fd が閉じられる）が観測しにくくなる**。
また L1-3 を直すと L1-1 の発火経路が閉じるので、**L1-1 単体の再現テストを先に固定しないと
直したことを確かめられなくなる。**

→ **L1-3 の修正と同時に、L1-1 の再現テストを置く**のが順序上の要点。

### 欠陥の種類（横断で探す対象）

> **「記録する」処理の失敗が、「記録される」処理の成否を変えている。**

DESIGN.md §5 が「ログのフレームワーク」を捨てた理由として
**「監査と診断は要求が正反対」「`LOG_LEVEL=error` で監査が黙って消える経路ができる」**
と書いている。**この文書は「監査が消える」方向を警戒しているが、
「監査の失敗が本体を壊す」方向は扱っていない。**

`src/` 内で同型を探した結果:

- `writeAudit`（`audit.ts:151-153`）は `server.ts` の `startup` / `startup-failed` からも呼ばれる。
  **`createHandlers` の catch 内（`server.ts:160-167`）で `writeAudit` が投げると、
  元の起動失敗の例外が失われる**（L1-3 と同型。起動時なのでプロセスは落ちるが、
  stderr に出る理由が別物になる）
- `stderrAuditSink`（`audit.ts:31-35`）は `process.stderr.write` が投げうる（EPIPE）

**同型が2箇所ある。** 段階3で扱う。

### 当時の意図（実装者コメント。コード由来）

`record()` を try の**内側**に置いたのは意図的で、狙いは「**成功でも失敗でも必ず1件残す**」こと
（`audit.ts:189` のコメント「握りつぶさない（規約 §5.4）。記録してから元の例外をそのまま投げ直す」）。

**シンクが投げる場合を考えていない。** 実装者は「記憶に裏づけが無い」としつつ、状況証拠を2つ挙げている。

1. `AuditSink`（`audit.ts:19-21`）は `write(line: string): void` だけで、**投げるかどうかを契約していない**
2. `multiAuditSink`（`audit.ts:37`）のコメント「1つが失敗したら**起動を続けない**」は
   **起動時の話**をしているが、実装は稼働中も同じものが走る

### 再現テストの書き方自体が設計判断になる（実装者コメント）

`createFileAuditSink(dir)` は `dir` を受けるだけで、**`openSync` を失敗させる注入口が無い。**
テストから L1-1 を再現するにはディレクトリを消す・権限を落とすなどの外部操作が要る。
順序上「L1-3 を直す前に L1-1 の再現テストを固定する」必要があるので、
**その書き方をどうするかが段階4の論点に入る。**

### 今回の対象外だが記録（実装者コメント）

`withAudit.listTools`（`audit.ts:166-168`）は**素通しで何も記録しない。**
今は `tools/list` が純粋な配列生成なので問題にならないが、
**根D（schema を policy / masters の関数にする）を当てると `tools/list` の内容がスコープに依存する。**
そのとき「何を公開したか」が監査に残らない形が残る。**根D を当てる段で一緒に決める論点。**

### 実測（2026-09-07・Node v24.18.0・統合者が自分で走らせた）

**L1-1 の再現**（実装者ノート §5 の probe をそのまま実行）:

```
現行（fd を戻さない）   初期fd=20 markerFd=20  marker の書き込み先: **別ファイルに入った**
提案（fd = -1 を足す）  初期fd=20 markerFd=20  marker の書き込み先: OK（自分のファイルに入った）
```

**`EBADF` は起きない。** 閉じられた番号を次の `openSync` が即座に取り直すので、
巻き添えの `write` は**成功したまま中身が監査ログのファイルへ入る**（規約 §5.4 の沈黙の失敗）。
L1 の報告（`EBADF` で落ちる）より1段悪い。**再現テストは「書いた内容がどのファイルに入ったか」で固定する** —
「fd が生きているか」では番号が再利用されるので素通りする。

**sonic-boom 5.0.1（＋ `atomic-sleep` 1.0.0）の確認:**

| 確かめたこと        | 結果                                                                                                |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| 型定義              | 同梱（`types/index.d.ts`）。**ただし型と実行時が正反対**（下記）                                    |
| 構築の失敗          | **同期送出**（`ENOENT`）。現行の起動時 `ConfigError` にそのまま対応する                             |
| `reopen` の失敗     | **同期送出**（`EACCES`）。リスナがあれば `'error'` にも流れる（両方）                               |
| 失敗後の書き込み    | **古い fd を保持したまま書き続ける**（実測 `"day06\nafter\n"`）。**開けてから閉じる**ので混入しない |
| `uncaughtException` | 上記の経路では**出なかった**                                                                        |

**型と実行時が逆になる**（採用時の罠）:

- `import SonicBoom from 'sonic-boom'` — 実行時は動くが、**型では namespace 扱いで `new` できない**（TS2709 / TS2351）
- `import { SonicBoom } from 'sonic-boom'` — **型は通るが、実行時は読み込み時 `SyntaxError`**
  （`SonicBoom.SonicBoom = SonicBoom` という property 代入なので Node の lexer が検出できない）

両方を満たす書き方（`as` 不要。型検査・実行・lint すべて通過を確認）:

```ts
import SonicBoomModule from 'sonic-boom';
import type { SonicBoom } from 'sonic-boom'; // 型だけ。実行時に消える
new SonicBoomModule.SonicBoom({ dest, append: true, mkdir: true, mode: 0o600, sync: true });
```

**sonic-boom にも同種の欠陥がある**（`index.js:527-531`）。`reopen` は `this.once('ready', …)` を
**開く前に**登録するので、開けなかったときリスナが残る。次に成功したとき古いリスナと新しいリスナの
両方が走り、**同じ fd を2回 close する**（実測で `[event] EBADF: close`）。ただし性質が違う。

|                | `fdFor`（現行）                      | sonic-boom                                           |
| -------------- | ------------------------------------ | ---------------------------------------------------- |
| 発火           | ローテーション失敗＋2回目の書き込み  | 失敗した `reopen` の**後に成功した** `reopen`        |
| 決定性         | **決定的**                           | 同一 tick 内の2回の close の隙にしか入れない狭い競合 |
| 失敗時のデータ | **巻き添えのファイルへ混入（沈黙）** | 古い fd を保持したまま書き続ける（失われない）       |
| 気づけるか     | 誰も気づかない                       | `'error'` に `EBADF` が流れる                        |

**裁定「止める」を入れると sonic-boom 側の経路は到達不能になる**（失敗したら回復しないので
「後に成功した reopen」が存在しない）。それでも `fdFor` の不変条件を直すのは、
**到達不能を根拠に放置しない**ため（裁定が将来「続ける」に変われば復活する）。

## 裁定（人間の決定・2026-09-07）

**稼働中に監査ログが書けなくなったら、サーバを止める。** ただし現状の事故とは別物として、
**意図した停止**にする。

1. **直前の1件には、手元にある `ToolResult` をそのまま返す** — 成功なら成功として返す。
   実行済みの操作を失敗として見せない（L1-3 の壊れ方1 を直す側が再生産しない）
2. **同じ応答に、利用者への告知を1ブロック足す** — 「監査に記録できないので停止する。
   この操作は実行済みなので再実行しないこと。出力先が書けるかとディスクの空きを確かめて起動し直すこと」
3. **具体的なパスと errno は stderr に留める**（`server.ts:158-159` の「種類だけ書き、本文は stderr」と同じ切り方）
4. **「起動に失敗しました」とは出さない**

### 告知を LLM が読む面に出す理由

**宛先は利用者で、LLM はその経路にすぎない。** 理由が付いた形で利用者に届く経路は実質これ1本しかない。

- stderr — MCP 仕様上クライアントが **ignore してよい**（`audit.ts:27-29` が監査ログについて既に同じ判断をしている）
- プロセス終了 — クライアントは「切断された」を見せるが、**なぜ止まったかは運ばない**（見せ方はクライアント次第・未検証）
- ツール結果の `content` — LLM が読み、利用者に話す

**`isError: true` には載せない。** 仕様（`tools.md` §Error Handling・2026-07-28）は
`isError` を「モデルが**自己修正して再試行**するための actionable feedback」と定義しており、
**再試行こそ最悪の結果**（Backlog への投稿は済んでいるので二重投稿になる）。
`content` がブロックの配列であることは仕様どおりなので、告知は別ブロックで足せる。

## 段階4 — 方針（2026-09-07 確定）

### 何を変えるか

**設定ではなく構造で守る。** 停止機構を optional の引数で渡す形にしない
（渡し忘れると挙動が変わる = 実装者ノート §4 が sonic-boom の `'error'` リスナについて
名指ししている失敗と同じ形）。**例外の型で運ぶ。**

1. **`AuditSink` の契約**（`audit.ts:14-22`）— `write` は**投げうる**ことを TSDoc に書く。型は変えない
2. **`withAudit`**（`audit.ts:170-193`）— シンクの失敗を捕え、**手元の `ToolResult` を載せた専用の例外**を投げる。
   結果を捨てない。元の例外は `cause` に残す（規約 §6.2）
3. **`serve`**（`stdio.ts:39-62`）— `handleMessage` と `channel.write` を try で包む。
   - 専用の例外 → 結果＋告知を1件の応答として書き、ループを畳む（意図した停止）
   - それ以外の例外 → `RPC_ERROR.INTERNAL` を返して**読み続ける**（1リクエスト1応答）
   - `channel.write` が投げる（EPIPE）→ 応答を書く先が無いのでループを畳む
4. **`createFileAuditSink`**（`audit.ts:65-99`）— 手書きの fd 状態機械を **sonic-boom** に置き換える。
   `AuditSink` の形（`write(line): void`）は変えないので、外から見た契約は同じ
5. **`runServer` / `main.ts`** — 意図した停止と起動失敗を言い分ける
6. **文書** — `DESIGN.md §5`（フレームワークを捨てた行）・`README.md`（監査ログの節）に稼働中の方針を書く

**シグネチャは変えない。** `withAudit` も `serve` も引数が増えないので、**既存テストは1件も動かない**と予測する
（C-1 と同じ判定基準）。

**限界を明記する。** これは根A のように**型で到達不能にする**形ではない。`serve` が catch を書かなければ成立しない。
守るのは「1リクエストに必ず1応答」の不変条件テストで、外せばそこが赤になる。

### どの指摘が閉じるか

**L1-3・L1-1・L1-2 ＋ L4-4**（`withAudit` の例外経路が未テスト。根F から移す。人間の承認済み）。
