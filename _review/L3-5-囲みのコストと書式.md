### 実装者の見立ては前提が成り立たない（検証済み）

実装者コメント（`01-実装者コメント.md:395-400`。本人が「未検証」と明記）は

手を入れて、得るものがゼロという形になっている。**採らない。**

> 評価できる点は2つある。`nonce` の呼び出しごとの乱数を「うっかり捨ててよいもの」に
> しない歯止めとして働くこと。測れない問い（モデルが同一 `nonce` の囲みをどう読むか）を
> **測っていないと明示している**こと。

## 段階4 — 方針（2026-09-07 確定）

### 何を変えるか

1. **`wrapUntrusted` から注意書きの行を落とす**（`untrusted.ts:113`）。
   境界（`source` ＋ `nonce` ＋ 開始／終了タグ）は値ごとに残す
2. **`UNTRUSTED_NOTICE` と、そこに付いている「気休め」の TSDoc を、ツール結果の出口へ移す**
   （`tools.ts:2505` の `buildHandlers.callTool`）。**囲みを含む応答にだけ、1回だけ載せる**
3. **置き場所は `content` の末尾**（`content[1]`）。先頭に置くと `content[0]` を読む16件が動く
4. **新しい不変条件をテストで固定する** — 「囲みを含む応答には注意書きが1回だけ載る」
   「囲みを含まない応答には載らない」

**`instructions` には寄せない**（クライアント依存。根C の論法と矛盾する）。
**`nonce` の設計は触らない**（実装者の案は前提が成り立たない）。

### 効果

**接地できるのは単価だけ。** 絶対値は実データが要る。

|                | バイト/囲み                     |
| -------------- | ------------------------------- |
| 今             | **254**                         |
| この変更のあと | **107**（＋ 応答ごとに1回 146） |

**単価は 58% 下がる。**

**個数は接地していない。** L3-5 の「20件で 5,040 バイト」は 252×20 ＝ 20囲みを前提にしているが、`search_issues` は `get_issue` と**同じ `shapeIssue`** を使い（`tools.ts:1278`）、**`summary` と `description` の両方を囲む**（`tools.ts:675` / `:704`）。カスタム属性も1つにつき1囲み。**構造上の下限は1課題あたり2囲み**なので、20件なら40囲み以上になる。

**L3-5 の数字を基数に使わない。** 統合者は当初この表を「今20 → 根B で80」で書いたが、それは**再現していない数字から導いた基数**だった（L3-5 の実測は再現していないと自分で書きながら、そこから出る 20 を使っていた）。実装者コメント §8.6 の指摘で気づいた。

言えるのは **「囲みの個数がいくつであれ、定型文は 58% 減る」** ことだけ。実データでの絶対値は根B の段で測り直す（下記）。

**L3-5 のみ。** 根B は閉じない（別コミット・別の根）。

### 影響範囲と、変更しないと決めた箇所

- 変えるのは `src/tool/untrusted.ts` と `src/tool/tools.ts` の2ファイル
- **既存テストは1件も動かない**と予測する（末尾に足すため。C-1・根C と同じ判定基準）
- **変えない**: `nonce` の乱数（抜けられない性質）／`renderSource` のサニタイズ／

### 測れないこと（人間の裁定の対象。2026-09-07 に裁定済み）

**注意書きを1回にして緩和の効果が落ちないかは測れない。** クライアントとモデル次第。
ただし DESIGN.md §8 は既に「囲みは緩和であって防御ではない。**対策済みとして数えない**」
「実際に効くのはツール面を絞ることと監査の2つ」と宣言しており、**その2つは1つも減らない**。
したがってこれは「防御を削る判断」ではなく「気休めの単価を下げる判断」。

**末尾と先頭のどちらが効くかも測れない。** だから **測れないので、副作用の小さい側（既存テストが動かないほう）を採る**、という順序で決める。

> **理由の順序を逆に書かない。** 「既存テストが動かないから末尾」と書くと、**測れる基準を、測れない問いの答えとして提示する**形になる。これはこのレビューで3回出た誤りと同じ形（`git log -S` の3回の誤読・「実測」ラベルの過信）。seam の基準はリファクタの置き場を決めるためのもので、**緩和をどこに置くと効くかには答えていない**（実装者コメント §8.6-2 の指摘）。

## 根B へ持ち越す論点（段階3 で洗うこと）

### 単価 × 個数の、個数側

**この方針が触るのは単価だけで、個数は手つかず。** 1課題あたり `summary` ＋ `description`（＋ カスタム属性の数）を囲んでおり、根B はそこへ3つ足す。

台帳は「絞り込みを入れた後の実データで測り直してから決める」と記録しており、**絞り込みは `fe51cb8` で入っている＝測り直す前提は揃っている**（実装者コメント §8.6-1）。**根B の段で実データを取り、個数側を扱うかを決める。**

**「`pickName` の中で囲む」は確定ではない。** 根B と実装者コメントは
「`pickName` の中で囲むほうがフィールド漏洩の要件を落とさない」としているが、
**`pickName` はユーザー専用ではない** — `issueType` / `status` / `priority` / `resolution`
（管理者が定義した閉じた選択肢）も同じ関数を通る（`tools.ts:677-680`）。
中で無条件に囲むと**過剰になり、コードベース自身の「第三者が書けるか」という軸に反する。**

`pickUserName` を作って内部で `pickName` を呼べば、PII の「唯一の経路」を保ったまま
過剰も避けられる。**この選択肢は根B にも実装者コメントにも挙がっていない。**

`pickName` の呼び出し27箇所のうち、ユーザー由来は **15箇所**
（`assignee` 2・`createdUser` 8・`updatedUser` 5）。

**`tags`（Wiki / Document の3箇所）は未確認。** Backlog のタグを誰が作れるかを確かめていない。
第三者が作れるなら根B と同じ種類だが、**未確認なので主張しない。**
