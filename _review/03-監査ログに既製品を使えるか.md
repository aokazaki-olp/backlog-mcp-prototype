# 実装者コメント — 監査ログに既製品を使えるか（根C の材料）

書いた側: **`src/` を実装したセッション**。**修正はしない。**
`01-実装者コメント.md` と同じ扱いで、**段階3・4 を通す側の入力**として置く。

きっかけは「これだから既存のパッケージを使いたかった」という一言。
**ロギングフレームワークではなく、この監査ログに最適化された部品があるか**を調べ、実際に動かした。

| 印         | 意味                                               |

## 0. 結論

**フレームワークには無い。部品にはある** — `sonic-boom`。ただし**採用しても L1-1 しか消えず、
その L1-1 は1行で塞がる。** そして採用すると根C の設計判断がライブラリの都合で決まってしまう。

**順序の提案**: ① L1-1 を1行で塞ぐ → ② 根C を人間が裁定する → ③ そのうえで採否を決める。
逆順にすると、**EventEmitter の既定が設計判断を代行する。**

## 2. 「レベルを ALL で固定する」案について

壁打ちで出た案。**成立する。私が先に挙げた反論のうち2つは崩れた。**

- **同期書き込みは pino にある**（確認・`docs/api.md`）: `sync: true // Synchronous logging`
- **レベル固定も書ける**: 生成時に `level: 'trace'` を渡し、その instance では env を読まない

**それでも崩れないのは1点。** 同じ `docs/api.md` の1103行目:

```
### `logger.level` (String) [Getter/Setter]
```

**Setter である。** `logger.level = 'silent'` の1行で消え、しかも
「the `silent` log method is a **noop function**」なので**投げも警告もしない**。

|                                         | 監査を消す口                            |
| --------------------------------------- | --------------------------------------- |
| 今の形（`AuditSink.write(line): void`） | **存在しない。** レベルという概念が無い |
| レベル固定                              | **存在するが、正しく設定してある**      |

原則1 の「その値を作れる口を用意しない」に照らすと、後者は**捨てたほうの形**。
そして根A が実証したのは「生成時に正しく貼ったが、2つ目の生成点で落ちた」壊れ方だった。

> **§5 の理由づけは薄い（実装者としての自己申告）。**
> §5 が書いているのは「`LOG_LEVEL=error` で監査が黙って消える経路ができる」で、
> これは**設定の問題として書かれている**。設定の問題なら設定で塞げる。
> **本当の理由は「監査にレベルという概念を持ち込まない」ほうで、そちらが書かれていない。**
> §5 は正しい結論に弱い理由を付けている。

## 3. `sonic-boom` — 条件を満たす部品（フレームワークではない）

**pino の `destination` そのもの**（`pinojs/sonic-boom`）。

|                 |                                             |
| --------------- | ------------------------------------------- |
| 版 / ライセンス | **5.0.1** / MIT                             |
| リリース        | **65回**、2017-12-23〜2026-08-31（**9年**） |
| 依存            | **1つ**（`atomic-sleep` 1.0.0・依存0・MIT） |

| 条件             | sonic-boom                                                                       |
| ---------------- | -------------------------------------------------------------------------------- |
| 同期書き込み     | `sync`: perform writes synchronously                                             |
| 耐久性           | `fsync`: perform a `fsyncSync` every time a write is completed（**今より強い**） |
| ローテーション   | **`reopen([file])` — 新しいファイル名を渡せる**                                  |
| パーミッション   | `mode`                                                                           |
| ディレクトリ作成 | `mkdir`                                                                          |
| **レベル**       | **無い。ロガーではないので概念そのものが存在しない**                             |
| worker thread    | 使わない（worker は `pino.transport` 側）                                        |

**DESIGN.md §5 の反論はこれには掛からない。** §5 が測っていたのは pino / winston / bunyan という層で、
**その下の層を見ていなかった。**

現在の `createFileAuditSink` と1対1で対応する。

| 手書きしている部分                            | sonic-boom                                  |
| --------------------------------------------- | ------------------------------------------- |
| `mkdirSync(dir)`                              | `mkdir: true`                               |
| `openSync(path, 'a', 0o600)`                  | `dest` + `append` + `mode`                  |
| `writeSync(fd, line)`                         | `write()` + `sync: true`                    |
| **`closeSync(fd)` → 新しい日付で `openSync`** | **`reopen(newPath)`**                       |
| （無し）                                      | `fsync` / `retryEAGAIN` / `maxWriteRetries` |

**L1-1 が住んでいるのは太字の行だけ。** 日付でファイル名を決める部分は3行の純粋な計算で、欠陥は無い。

## 4. 実機で確かめた（2026-09-06・Node v24.20.0・`sonic-boom@5.0.1`）

**本体リポジトリは触っていない。** スクラッチパッドに別プロジェクトを作り、
`npm install sonic-boom` で**2パッケージだけ**（`sonic-boom` + `atomic-sleep`）を入れて動かした。

| 確かめたこと            | 結果                                                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| CJS を ESM から読めるか | **`import SonicBoom from 'sonic-boom'` は動く。`import { SonicBoom }` は `undefined`**（namespace は `default` と `module.exports` のみ） |
| `sync: true` の書き抜け | **無い。** `minLength` 既定は `0`。`write()` 直後に `readFileSync` で読める                                                               |
| `mode` / `mkdir`        | **効く。** `0o600` を渡してパーミッション `600`                                                                                           |
| `fsync: true`           | **動く**                                                                                                                                  |

### 失敗の伝わり方 — 採用判断の核心（確認）

```
listener あり  → 同期送出 なし   / 'error' イベントに ENOENT
listener なし  → write() が同期的に throw (EBADF) / イベントなし
```

EventEmitter の標準的な挙動だが、**採用すると根C の裁定が「リスナを付けるかどうか」で表面化する。**

- リスナを付ける = **稼働中は本体を続ける**（監査の失敗が呼び出し側に届かない）
- 付けない = **本体に伝える**（今と同じ）

**付け忘れると挙動が変わる。** 2節の「レベル固定」案と同じ形で、**設定で守るのであって構造ではない。**

> `reopen()` の失敗だけは別で、**listener があっても同期送出され、かつイベントにも流れる**（両方）。
> ソースの `catch (err) { fileOpened(err); throw err }` のとおり。

### L1-1 の等価シナリオでは、sonic-boom が正しい（確認）

```
1) 初期 fd            : 21
2) reopen(開けない先)  : ENOENT を送出、fd は 21 のまま
3) marker が fd 22 を取る          ← 21 は解放されていない
4) reopen(良い先)      : 成功、fd = 23
5) marker はまだ生きているか : YES
6) 失敗前のファイルに行が残り、成功後のファイルに続きが入る
```

理由はソースにある（`node_modules/sonic-boom/index.js:527-538`）。

```js
const fd = this.fd; // 古い fd を控える
this.once('ready', () => {
  // 新しいのが開けたときだけ発火
  if (fd !== this.fd) fs.close(fd); // そこで初めて古いほうを閉じる
});
openFile(this.file, this); // 開く
```

**「開けてから閉じる」。** 今の `fdFor`（`audit.ts:75-86`）は逆で「閉じてから開く」なので、
開けなかったときに**閉じた番号だけが残る**。

## 5. L1-1 は1行で塞がる（再現つき・確認）

現行ロジックをそのまま写して走らせた結果。

```
現行（fd を戻さない）   初期fd=20 markerFd=20  marker の書き込み先: **別ファイルに入った**
提案（fd = -1 を足す）  初期fd=20 markerFd=20  marker の書き込み先: OK（自分のファイルに入った）
```

`closeSync(fd)` の直後に **`fd = -1;`** を1行足すだけ。

### L1 の報告より1段悪い形が出た（確認）

L1 は「無関係の fd が **`EBADF`** で閉じられる」と報告しているが、**この再現では `EBADF` は起きない。**
閉じられた番号を**次の `openSync` が即座に取り直す**ため、犠牲になった側の `write` は
**成功したまま、中身が監査ログのファイルへ入る。**

**エラーが出ないぶん、こちらのほうが重い**（規約 §5.4 の沈黙の失敗）。
どちらが起きるかはタイミング次第。**再現テストはこの形（書いた内容がどのファイルに入るか）で固定すべき。**
「fd が生きているか」だけを見ると**素通りする** — 番号は再利用されるので生きているように見える。

### 再現コード（§8.3 の「違反コードを1件書いて落ちる」にそのまま使える）

```js
// P6b - fd 番号が再利用されるので「生きているか」では足りない。
// marker へ書いた内容が marker.txt に入っているかまで見る。
import { closeSync, mkdtempSync, openSync, readFileSync, writeSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const makeFdFor = (pathOf, resetOnClose) => {
  let openedDate = '';
  let fd = -1;
  return date => {
    if (date === openedDate) {
      return fd;
    }
    if (fd !== -1) {
      closeSync(fd);
      if (resetOnClose) {
        fd = -1;
      }
    }
    fd = openSync(pathOf(date), 'a', 0o600);
    openedDate = date;
    return fd;
  };
};

const probe = (label, resetOnClose) => {
  const dir = mkdtempSync(join(tmpdir(), 'fdfor-'));
  const pathOf = date =>
    date === '2026-09-07'
      ? join('/nonexistent-dir-xyz', `audit-${date}.jsonl`)
      : join(dir, `audit-${date}.jsonl`);

  const fdFor = makeFdFor(pathOf, resetOnClose);
  const first = fdFor('2026-09-06');
  writeSync(first, 'day06\n');

  try {
    fdFor('2026-09-07');
  } catch {
    /* ローテーション失敗 */
  }

  const marker = openSync(join(dir, 'marker.txt'), 'w');
  try {
    fdFor('2026-09-08');
  } catch {
    /* 2回目 */
  }

  let verdict;
  try {
    writeSync(marker, 'MARKER-OWN-DATA\n');
    const inMarker = readFileSync(join(dir, 'marker.txt'), 'utf8').includes('MARKER-OWN-DATA');
    const inAudit = readFileSync(join(dir, 'audit-2026-09-08.jsonl'), 'utf8').includes(
      'MARKER-OWN-DATA',
    );
    verdict = inMarker
      ? 'OK（自分のファイルに入った）'
      : inAudit
        ? '**別ファイルに入った**'
        : '行方不明';
  } catch (e) {
    verdict = `write が失敗 (${e.code})`;
  }
  console.log(
    `${label.padEnd(24)} 初期fd=${first} markerFd=${marker}  marker の書き込み先: ${verdict}`,
  );
  try {
    closeSync(marker);
  } catch {}
};

probe('現行（fd を戻さない）', false);
probe('提案（fd = -1 を足す）', true);
```

## 6. 見立て

**採用は「あり」の側に振れたが、L1-1 に対しては「1行 vs 依存2つ」。**

そして採用すると根C の裁定が EventEmitter の作法に引きずられる。**それは §5 が
「監査がレベル体系に載る」を嫌ったのと同じ形の失敗**なので、順序を守ってほしい。

1. **L1-1 を1行で塞ぐ**（上の再現をテストにする）
2. **根C を人間が裁定する** — 稼働中に監査が書けなくなったらどうするか
3. **裁定に合わせて sonic-boom の採否を決める** — 「続ける」なら listener あり、
   「伝える」なら listener なし。**決めた側に合わせて配線する**

**DESIGN.md §5 は書き直す価値がある。** 「非同期だから」「レベルで消えるから」を根拠にしていると、
**設定で答えられて理由が崩れる**（実際、2節で2つとも崩れた）。書くべきは
**「監査は消せる口を持たない」**で、それは根A の修正（生の gateway を持たせない）と同じ原理。
**同じ原理が2箇所で効いているなら、原則として書ける段階に来ている。**
