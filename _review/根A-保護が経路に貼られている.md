## 段階1 — 理解

指摘者の言葉から離すと、症状はこうなる。

> **Backlog から返ってきた文字列が、経路によって扱いが変わる。**
> `send` を通る経路では `<untrusted>` で囲まれ `ApiFailureError` になり `cause` が繋がるが、
> `sendBytes` を通る経路（添付のダウンロード）では**そのどれも起きず、生のまま LLM へ返る**。

視点ごとの見え方が違うだけで、症状は1つ。

| 視点  | 何として報告されたか                                                                               |
| ----- | -------------------------------------------------------------------------------------------------- |
| L1-6  | 例外が `ApiFailureError` にならず `cause` チェーンも作られない（監査ログの `thrown` が別名になる） |
| L2-2  | 第三者が書いた文字列が無囲いで LLM に届く（プロンプトインジェクションの流入口）                    |
| L3-10 | 同じ失敗が経路によって文言の形が違う                                                               |

## 段階2 — 調査（接地）

### 何が起きているか

`sendRequest`（`src/tool/tools.ts:1941`）が包んでいるのは **`context.gateway.send` だけ**。

`runTool`（`src/tool/tools.ts:1968-2012`）の分岐を並べると、保護の掛かり方が3通りある。

| 種別             | `sendRequest` を通るか | なぜ                                                                                                           |
| ---------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| `send` / `chain` | 通る                   | **共通の末尾** `const raw = await sendRequest(...)` に落ちる。書き手が何も判断しなくても付いてくる             |
| `both`           | 通る                   | 明示的に2回呼んでいる（書き手が考えて、正しく書いた）                                                          |
| `download`       | **通らない**           | **早期 return する**（`return planned.shape(await receive(bytes, planned.fileName))`）。共通の末尾に到達しない |

`both` を足したときは `sendRequest` を明示的に呼んでいる。つまり書き手はこの保護を認識していた。
`download` で外れたのは、**早期 return する枝だったから**。

### 同じ穴から出るもの

`src/domain/backlogGateway.ts:61` の裸の `Error`
（`${request.endpoint} からバイト列を受け取れませんでした`）も、この口から素通しで出る。
L3-15（内部エンドポイントパスの露出）と接している。

### 経緯（`git log -S` で確認）

```
613016b  sendRequest を導入
11c83d0  添付のダウンロードを足す ← download / sendBytes を追加（HEAD の3つ前）
```

`sendRequest` の TSDoc はこう書いている。

> **層で分けているので、エラー名の一覧を持たなくてよい** —
> この try の内側から出てきたものは定義上すべて「下から来たもの」

**この推論は `send` が外への唯一の口であるうちは正しい。** `sendBytes` がその前提を壊したが、
TSDoc は見直されていない。`src/domain/gateway.ts` を読むと **なぜ口を2つに分けるかは
非常に丁寧に検討されている**（借り物の `BacklogApiClient` が `responseHandler` を焼き込んでいて
バイナリ応答で `body` が `null` になる）。検討されなかったのは
**1つ目の口に何が貼り付いていたか**のほう。

### 欠陥の種類（横断で探す対象）

> **保護が「境界」ではなく「特定のメソッド呼び出し」に貼られており、
> 早期 return する分岐がそれを迂回できる。**

`src/` 内で同型を探した結果:

- `runTool` の `attach` 分岐（`context.readAttachment`）も早期 return ではないが `continue` で
  共通の末尾を通らない。ただしこちらは**そもそも gateway を呼ばない**ので該当しない
- `runTool` の `none` 分岐も同様に該当しない
- **`sendBytes` を呼ぶ箇所は `download` 1つだけ**（`grep` で確認）

**現時点で同型は他に無い。** ただし「3つ目の口が生えたら同じことが起きる」構造は残っている。

### 修正案の分類

| 分類         | 判定                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| **書くべき** | 該当。`download` 経路の失敗が LLM に渡る形が、他の経路と揃っていない。揃えないと L2 が実証した流入口が開いたまま |

## 段階3 — 整合性の確認（**未了**）

### 確定した制約 — DESIGN.md §4

統合時に「包みを gateway 側へ移す」案を推奨として出した。**これは却下した。**

DESIGN.md §4（層と語彙、`DESIGN.md:152-160`）:

| 層        | 知ってよい                                                | 知ってはいけない  |
| --------- | --------------------------------------------------------- | ----------------- |
| `domain/` | projectKey, issueKey, 「バグ」「高」などの名前            | MCP, スコープ     |
| `tool/`   | tool 名, inputSchema, annotations, content, **untrusted** | HTTP, status code |

**`untrusted` は `tool/` の語彙として名指しされている。** `domain/backlogGateway.ts` に
`wrapUntrusted` を持ち込むのは表に反する。

> 補遺の実例4と同じ形だった。指摘の接地が強かったので提案まで確からしく見え、
> **成果物自身の内部原則との照合をしていなかった**。照合先は DESIGN.md の中にあり、
> レンズの報告の側には無い。

### 残る選択肢

**案1 — `sendBytesRequest` を作る。**
§4 を満たす。最小の変更で、`download` 分岐が新しい包みを呼ぶだけ。
**弱点**: 3つ目の口が生えたら同じことが起きる。保護は依然「呼び出しごとに貼る」形。

**案2 — tool 層の中で構造を閉じる。**
`runTool` の全分岐が gateway 呼び出しを1箇所に通す形にする。§4 を満たしたまま
「貼り忘れ」を構造で消せる可能性がある。
**弱点**: `send` は `unknown` を、`sendBytes` は `Uint8Array` を返すので、
1つの関数に畳むと型が緩む恐れがある。**未検証。**
