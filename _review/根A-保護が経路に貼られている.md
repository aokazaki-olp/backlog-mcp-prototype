## 段階1 — 理解

指摘者の言葉から離すと、症状はこうなる。

> **Backlog から返ってきた文字列が、経路によって扱いが変わる。**
> `send` を通る経路では `<untrusted>` で囲まれ `ApiFailureError` になり `cause` が繋がるが、
> `sendBytes` を通る経路（添付のダウンロード）では**そのどれも起きず、生のまま LLM へ返る**。

視点ごとの見え方が違うだけで、症状は1つ。

| 視点  | 何として報告されたか                                                                               |
| ----- | -------------------------------------------------------------------------------------------------- |
| L1-6  | 例外が `ApiFailureError` にならず `cause` チェーンも作られない（監査ログの `thrown` が別名になる） |
| L2-2  | 第三者が書いた文字列が無囲いで LLM に届く（プロンプトインジェクションの流入口）                    |
| L3-10 | 同じ失敗が経路によって文言の形が違う                                                               |

## 段階2 — 調査（接地）

### 何が起きているか

`sendRequest`（`src/tool/tools.ts:1941`）が包んでいるのは **`context.gateway.send` だけ**。

`runTool`（`src/tool/tools.ts:1968-2012`）の分岐を並べると、保護の掛かり方が3通りある。

| 種別             | `sendRequest` を通るか | なぜ                                                                                                           |
| ---------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| `send` / `chain` | 通る                   | **共通の末尾** `const raw = await sendRequest(...)` に落ちる。書き手が何も判断しなくても付いてくる             |
| `both`           | 通る                   | 明示的に2回呼んでいる（書き手が考えて、正しく書いた）                                                          |
| `download`       | **通らない**           | **早期 return する**（`return planned.shape(await receive(bytes, planned.fileName))`）。共通の末尾に到達しない |

`both` を足したときは `sendRequest` を明示的に呼んでいる。つまり書き手はこの保護を認識していた。

### なぜ落ちたのか — 「うっかり」ではなく型の形（実装者コメント。統合者が確認）

当初ここに「早期 return する枝だったから」と書いた。**症状であって理由ではない。**

共通の末尾は `const raw = await sendRequest(...)` で **`unknown` を配る**形になっている。
一方 `download` の `shape` は `PlannedCall` の定義（`tools.ts:119-124`）で
**`(received: ReceivedAttachment) => unknown`** と決まっており、**`unknown` を取らない。**
つまり `download` は共通の末尾に**合流できず**、独立した枝として書くしかなかった。

`both` が通ったのは「早期 return しなかったから」ではない（`both` も早期 return する）。
**`send` と同じ `unknown` を扱っていて `sendRequest` がそのまま使えた**からで、
`download` は使えなかったので**その場で `gateway.sendBytes` を直接呼んだ**。

> **統合者の確認**: `PlannedCall` の `download` 分岐の `shape` シグネチャを実物で確認した（2026-09-06）。

### 壊れた不変条件（段階3の起点。当初の記述を訂正）

当初は「`download` が末尾を通らない」を欠陥と書いた。**不変条件はそちらではない。**

> **gateway を呼ぶ枝は `sendRequest` を通る。**

枝は現在3つある（末尾の `send`/`chain`・`both`・`download`）。
**この形で書き出すと、修正は「末尾に合流させる」ではなく「3つの枝すべてが通る場所を作る」になる。**

### 同じ穴から出るもの

`src/domain/backlogGateway.ts:61` の裸の `Error`
（`${request.endpoint} からバイト列を受け取れませんでした`）も、この口から素通しで出る。
L3-15（内部エンドポイントパスの露出）と接している。

### 経緯（`git log -S` で確認）

```
613016b  sendRequest を導入
11c83d0  添付のダウンロードを足す ← download / sendBytes を追加（HEAD の3つ前）
```

`sendRequest` の TSDoc はこう書いている。

> **層で分けているので、エラー名の一覧を持たなくてよい** —
> この try の内側から出てきたものは定義上すべて「下から来たもの」

**この推論は `send` が外への唯一の口であるうちは正しい。** `sendBytes` がその前提を壊したが、
TSDoc は見直されていない。`src/domain/gateway.ts` を読むと **なぜ口を2つに分けるかは
非常に丁寧に検討されている**（借り物の `BacklogApiClient` が `responseHandler` を焼き込んでいて
バイナリ応答で `body` が `null` になる）。検討されなかったのは
**1つ目の口に何が貼り付いていたか**のほう。

### 欠陥の種類（横断で探す対象）

> **保護が「境界」ではなく「特定のメソッド呼び出し」に貼られており、
> 早期 return する分岐がそれを迂回できる。**

`src/` 内で同型を探した結果:

- `runTool` の `attach` 分岐（`context.readAttachment`）も早期 return ではないが `continue` で
  共通の末尾を通らない。ただしこちらは**そもそも gateway を呼ばない**ので該当しない
- `runTool` の `none` 分岐も同様に該当しない
- **`sendBytes` を呼ぶ箇所は `download` 1つだけ**（`grep` で確認）

**現時点で同型は他に無い。** ただし「3つ目の口が生えたら同じことが起きる」構造は残っている。

### 修正案の分類

| 分類         | 判定                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| **書くべき** | 該当。`download` 経路の失敗が LLM に渡る形が、他の経路と揃っていない。揃えないと L2 が実証した流入口が開いたまま |

### 残る選択肢

**案1 — `sendBytesRequest` を作る。**
§4 を満たす。最小の変更で、`download` 分岐が新しい包みを呼ぶだけ。
**弱点**: 3つ目の口が生えたら同じことが起きる。保護は依然「呼び出しごとに貼る」形。

**案2 — tool 層の中で構造を閉じる。**
`runTool` の全分岐が gateway 呼び出しを1箇所に通す形にする。§4 を満たしたまま
「貼り忘れ」を構造で消せる可能性がある。

**弱点として「`send` は `unknown`、`sendBytes` は `Uint8Array` を返すので型が緩む恐れ」と書いたが、
実装者コメントに反論がある（未検証）。**

> 型を1つに畳む必要は無い。**畳むべきは戻り値ではなく `catch` のほう**で、
> 「gateway を呼ぶ」だけを受け取り失敗したら囲む高階の関数にすれば、
> 中身が `() => Promise<unknown>` でも `() => Promise<Uint8Array>` でも同じ。
> **型パラメータ1つで済み `unknown` に落ちない。** `sendRequest` はその特殊化として残せるので、
> 既存の呼び出し3箇所を書き換えずに済む可能性がある。

**未検証。実装者自身も「測っていない」と書いている。** あわせて
**規約 §2.7（検証を伴わない型パラメータは `as` と等価）に当たらないか**を段階3で確かめること
（実装者は「値を作らず素通しするだけなので当たらないと考えているが、測っていない」としている）。

### 案4 — capability ではなく操作を渡す（Electron の contextBridge 形）

**DESIGN.md を Electron の契約モデルで読み直して出た案。統合者が書いた。未実装。**

#### 診断 — C-1 は「貼り忘れ」ではない

DESIGN.md の Electron 参照は4箇所あり、1つのモデルを作っている。

| 箇所              | 内容                                                                          |
| ----------------- | ----------------------------------------------------------------------------- |
| §2 原則4（`:80`） | `event.sender` から `ipcRenderer` に到達できる → 返り値から到達させない       |
| §4（`:162`）      | input 段は **preload と同じ役どころ**                                         |
| §4（`:165`）      | **プロセス境界が構造的に語彙を分けるから効く。1プロセスなのでこの強制が無い** |
| §5（`:205`）      | 汎用ツールを捨てた理由 → **「生の `ipcRenderer` を渡すな」と同型**            |

Electron のルールは2枚（**生の capability を渡さない** / **返り値から到達させない**）。
**この設計は LLM に面した境界には両方を当てている**（原則3・§5 と 原則4）。

**当てていない境界が `ToolContext` の中にある**（`tools.ts:66-77`）。

```ts
readonly gateway: BacklogGateway;                                    // ← 生の capability
readonly readAttachment?: (root, requested) => Promise<AttachmentFile>;      // ← 操作
readonly receiveAttachment?: (bytes, name) => Promise<ReceivedAttachment>;   // ← 操作
```

**同じインターフェースの中で、fs と gateway の渡し方が違う。** fs は `server.ts:141-149` で
設定を焼き込んだクロージャとして渡され、コメントは「**tool 層は `node:fs` を知らない**」——
これは contextBridge そのもの。gateway は生のまま渡り、tool 層は「`sendRequest` を通す」という
**約束**で守られている。

> **根**: tool 層が、安全な使い方が規律に依存する生の capability を持っている。
> **他所では規律に依存することを拒んでいる設計の中で、ここだけ依存している。**

lint も止められない。`tool/` が `domain/gateway.ts` を import するのは**意図された契約**なので
`no-restricted-imports` の対象外。**lint の境界はモジュール単位、違反はメソッド単位。**
§4 が「一部だけ機械強制側へ持ってきている」と書いている、その残り半分に C-1 が落ちている。

#### 形

原則1 の言い方を応答側へ適用する。「毎回 `sendRequest` を通す」ではなく
**「囲みの掛かっていない gateway が `runTool` から到達不能」**。

```
buildHandlers(context)          ← server.ts は今のまま gateway を渡す
  └ ここで call / callBytes を作る（囲みは tool/ に留まる。§4 の語彙表を満たす）
      └ runTool は call / callBytes しか持たない  ← 生の gateway がスコープに無い
```

**型が別物になるのが要点。** 案3 は包んだ後も `BacklogGateway` 型なので生のものと構造的に
交換可能だが、関数にすれば `createBacklogGateway(...)` の戻り値は**代入できない**。

**新概念ではない。`readAttachment` が既にやっている形の一般化**（補遺「文書内の錨を先に探す」）。

#### 3案との比較

|                             | 根を直すか               | 再発面                                      | コア設計との関係                        |
| --------------------------- | ------------------------ | ------------------------------------------- | --------------------------------------- |
| 案1 `sendBytesRequest`      | 症状                     | 残る                                        | 中立                                    |
| 案3 包んだ `BacklogGateway` | 直す                     | コンパイラが止める（**検証済み** `TS2741`） | 中立                                    |
| **案4 capability → 操作**   | **直す**                 | **到達不能**（型で別物）                    | **`readAttachment` の一般化。錨がある** |
| `accept` 化                 | 直さない（実装者の申告） | 口が増えない                                | 直交。併用できる。別件として立てる      |
