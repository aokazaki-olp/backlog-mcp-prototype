## 段階1 — 理解

指摘者の言葉から離すと、症状はこうなる。

> **Backlog のユーザーは自分の表示名を自分で決められるのに、
> このサーバは表示名を「管理者が定義した閉じた選択肢」として扱っている。**

### L2-3 の引用元は誤り（統合時に訂正済み）

> **ユーザーオブジェクトを出力に載せる唯一の経路。** Backlog のユーザーは
> `id` / `userId` / `name` / `roleType` / `lang` / `nulabAccount` / `mailAddress` /

### L1-4（別人に解決される）の機構

`toUserIds`（`masters.ts:140-175`）は **1つの `result` Map を2つの名前空間で共有している。**

```
ループ1:  result.set(loginName, id)     ← ログイン名の空間
ループ2:  for ([name, id] of byName)
            if (!ambiguous.has(name))
              result.set(name, id)      ← 表示名の空間。ログイン名の項目を上書きしうる
```

`ambiguous` が守っているのは **`byName`（表示名どうしの衝突）だけ**。
**表示名 × ログイン名の衝突は一切検査していない。**
ユーザーA（`userId: "sato"`）とユーザーB（`name: "sato"`）がいると、
`assignee: "sato"` は**Bに解決される**。`ambiguousUserNames` は空のままなので警告も出ない。

`toUserIds` の TSDoc は「**黙って先勝ちにしない**（規約 §5.4 — 別人に割り当てるのは静かな失敗）」
と明言している。**その当の失敗が、別経路で起きている。**

## 段階3 — 整合性の確認（**未了**）

### 書き出すべきもの（未着手）

**`pickName` の TSDoc が運んでいるもの。**
「ここを通す限り `name` しか出ない ので、経路を増やさないことが要件になる」——
この一文は**フィールド漏洩の要件**を運んでいる。信頼分類を足すときに、
この要件を落とさないこと。`pickName` を分割したり呼び出し側で囲む形にすると、
**「唯一の経路」という性質が崩れる**恐れがある。

**`lookupName` の TSDoc が運んでいるもの。**
「選べる名前をメッセージに載せる。LLM が自分で言い直せるようにするため」——
これは L3 が高く評価した**自己修正できるエラー文言**の根拠。
囲むと識別子として使いにくくなる可能性があり、**T-2（添付ファイル名）と同じ構造の対立**が
ここにもある。`lookupName` は7種類のマスタから呼ばれ、**ユーザーだけが自由記述**。
呼び出し元ごとに扱いを変えるのか、`lookupName` に判断を持たせるのかは未決。

**`list_project_masters` の `members` が運んでいるもの。**
DESIGN.md §9 が記録する2つの事故の産物（1人1件・`loginName` は省略可）。
**囲みを足すときにこの2つの性質を壊さない**こと。

**L1-4 を束ねるかどうか。**
L1-4 は同じ誤分類から出ているが、**修正箇所が違う**（囲みではなく索引の設計）。
束ねると「どの変更がどの指摘に対応したか」が追えなくなる恐れがある。
補遺は「迷ったら分ける側に倒す。ただし同根のものを分けるのは事故」としている。
**同根だが修正が独立、という中間の形。** 判断が要る。
