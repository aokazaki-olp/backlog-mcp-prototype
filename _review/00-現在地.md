  違反ゼロを確認している
- 統合者の通読でも、`policy.ts` の正規形展開と実行時凍結、`localFile.ts` の
  `realpath` → `isInside` → 単一ハンドルによる TOCTOU 対策は、**設計意図と実装が一致**している

**欠陥の多くは「後から足した機能が、既存の前提を壊した」形をしている。**
根A がその典型で、`sendRequest`（`613016b`）の TSDoc「この try の内側から出てきたものは
定義上すべて『下から来たもの』」は、`send` が外への唯一の口であるうちは正しかった。

**この形は、修正の当て方を決める。** 既存の判断を置き換えるのではなく、
**その判断が依存していた前提を明示し、前提が崩れる場所に構造を置く**方向が筋になる。
「元の設計が間違っていた」と読んで書き直すと、実証されている7系統の防御を壊しかねない。

**ただし根B は例外で、これは最初からの誤分類である。**

## 考察 — 進め方について

**1. 統合者が根分けを推論で行った（失敗）。**
第1巡の統合直後、36件を10の「根」に束ねて提示した。ソースを読まず、指摘文の主題が
似ているかで束ねたもの。通読して導出し直したところ **10のうち4つが誤り**だった。

補遺は「指摘の接地」と「修正案の接地」を要求しているが、**その手前の「根分けの接地」を
明示していない**。統合（どの指摘を採るか）と適用（どう落とすか）の境目にあるこの作業が、
規律の穴になっている。**補遺への申し送り。**

**2. 「実測」ラベルは正しさを保証しない（補遺の実例5が的中）。**
L1 の指摘は11件すべて probe で接地されていたが、**行番号が系統的に誤っていた**
（`audit.ts:364` → 実際 `:75`、`main.ts:339` → 実際は39行のファイル）。
実体は本物だったので、位置だけ統合者が引き直した。

同じことがこのファイルを書く直前にも起きた。`git log -S "result.set(loginName"` が
`a445d56` を返したので「L1-4 はこの commit で入った」と書きかけたが、差分を見たら
**この commit は既存の `result.set` を変数に括り出しただけ**だった。`-S` が拾うのは
文字列の増減であって構造の導入ではない。**道具の出力を、その道具が答えていない問いの
答えとして読んでいた。**

**3. レンズが一次情報の引用を捏造した（2026-09-06 発覚）。**
L2 は根B の裏取りとして Backlog ヘルプセンターの2記事の URL を挙げ「確認済み」と報告したが、
**`support-ja.backlog.com` はこの環境から 403**（Cloudflare のチャレンジ。curl / ブラウザ UA の
2通りで確認）。DESIGN.md:332 も「この環境から出られない」と既に記録していた。
ミラー（152エンドポイント）にも表示名の記述は0件。**L2 は読めない先を根拠に挙げている。**

補遺の実例5（報告された実測が再現しなかった）より悪い形で、**測っていないのではなく
出典そのものが成立していない**。しかも統合者はこれを台帳に「一次情報で確認済み」として
写していた。**接地された指摘に添えられた出典を、出典として検証していなかった。**

**原因の一端は統合者のレンズ設計にある。** L2 のプロンプトには
「Backlog API の一次情報が要るときは `developer.nulab.com` を参照する（記憶で答えない）」と
