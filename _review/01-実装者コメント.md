**`download` の `shape` は `unknown` を取らない。** `PlannedCall` の定義（`tools.ts:114-127`）で

> **段階3の材料として**: 壊れた不変条件は「`download` が末尾を通らない」ではなく、
> **「gateway を呼ぶ枝は `sendRequest` を通る」**のほう。枝は今3つある
> （末尾の `send`/`chain`・`both`・`download`）。

## 2. 根C — `record()` が try の内側にあるのは意図的。ただしシンクが投げる場合を考えていない

### 当時の意図（コード由来）

`withAudit` のコメント（`audit.ts:189`）は

意図していたのは「**成功でも失敗でも必ず1件残す**」ことで、
`record()` を try の内側に置いたのはそのため。

**シンクが投げる場合は考えていない。**（記憶・裏づけ無し。ただし次の2つが状況証拠になる）

1. `AuditSink`（`audit.ts:19-21`）は `write(line: string): void` だけで、
   **投げるかどうかを契約していない**。TSDoc にも書いていない
2. `multiAuditSink`（`audit.ts:37`）のコメントは
   「1つが失敗したら**起動を続けない**（黙って片方だけ書かない）」——
   **起動時の話をしている。** 実装は稼働中も同じものが走る

### fail-closed は起動時にしか書いていない（確認）

`server.ts:100-102`:

> ファイルに書けなければここで落ちる。監査に寄りかかった設計が監査なしで動くのは、
> 防御について嘘をつくことになる（fail-closed）

`createHandlers` の TSDoc（`server.ts:84-85`）も「途中で1つでも失敗したらハンドラを返さない」と
**起動時のことしか書いていない**。**稼働中の方針は、決めていないのではなく、書いていない。**
ノートが「これは設計の決定なので人間の判断領域」としているのに同意する。

### 順序の指摘に同意（確認）

「L1-3 を直すと L1-1 の発火経路が閉じるので、**L1-1 単体の再現テストを先に固定しないと
直したことを確かめられなくなる**」——`fdFor` の再現条件は
**`openSync` が投げた後にもう一度 `fdFor` が呼ばれること**なので、そのとおり。
`createFileAuditSink(dir)` は `dir` を受けるだけなので、
**テストからは `openSync` を失敗させにくい**（ディレクトリを消す・権限を落とすなどの外部操作が要る）。
ここは依存注入の口が無いので、**再現テストの書き方自体が設計判断になる**。

### 異議 — L1-2 は L1-3 の純粋な下流ではない（確認）

ノートは「**`serve` まで例外が届く経路は `withAudit` の再送出しかない**」と書いている。
`handleMessage` に限れば**そのとおり**（`parseRequest` / `initializeResult` / `discoverResult` は
すべて純粋で、どんな入力でも投げない。`assertNever` は型で到達不能）。

**ただし `serve` は `handleMessage` の外でも投げうる。**

```ts
// stdio.ts:59-61
const response = await handleMessage(message, handlers, serverInfo);
if (response !== null) {
  channel.write(JSON.stringify(response)); // ← ここ
}
```

`channel.write` は `main.ts:15-17` で `process.stdout.write` を呼ぶ。
**クライアントが先に落ちていれば EPIPE で投げる。** そのとき `for await` を抜け、
`main.ts` の catch が「**起動に失敗しました**」と出す。

つまり **L1-2（誤った文言と、ループごと死ぬこと）は L1-3 と独立に発火しうる。**
実害は小さい（stdout が壊れている時点でクライアントは居ない）が、
「L1-3 を直せば L1-2 は起きない」と読むと**取りこぼす**。順序の結論は変わらない。
