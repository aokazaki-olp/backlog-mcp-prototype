### なぜ落ちたのか — 「うっかり」ではなく型の形（確認）

`runTool` の共通の末尾はこうなっている。

**`download` の `shape` は `unknown` を取らない。** `PlannedCall` の定義（`tools.ts:114-127`）で

`both` も早期 return するが、そちらは `sendRequest` を明示的に2回呼んでいる。
**同じ日に書いた2つの枝で、片方は通し、片方は落とした。** 差は「合流できたか」ではなく、

> **段階3の材料として**: 壊れた不変条件は「`download` が末尾を通らない」ではなく、

### はじめから必要だったなら — 口ではなく `ResolvedRequest` の属性

**契約モデルとして正しい形はこちら**だと考えている。ただし**根A の修正ではない**（後述）。

`gateway.ts` の TSDoc は `ResolvedRequest` を「input 層が組み立て済み」の、
**その呼び出しの完全な記述**として位置づけている。だとすれば「応答をどう解くか」も
その記述の一部で、**メソッド名で表すものではない。**

```ts
readonly accept: 'json' | 'bytes'; // ResolvedRequest の属性
send(request): Promise<…>; // 口は1つのまま
```

こうしておけば `sendRequest` の TSDoc の等式（「この try の内側から出てきたものは定義上
すべて『下から来たもの』」）は**今も真だった**。口が1つなら、これは条件付きの真ではなく
**構造から出る真**になる。**今回の欠陥は「保護を貼り忘れた」ではなく、
貼る場所が口の数だけあったことが本体。**

#### いちばん効くのは、契約が実装都合を語らなくなること（確認）

`gateway.ts:22-32` は、**インターフェースの TSDoc で借り物の欠陥を説明している。**

> `send` と分けているのは、借り物のクライアントが応答を1通りにしか解けないため。
> `BacklogApiClient` は `responseHandler: response => response.body` を焼き込んでいて…

`gateway.ts` の冒頭は「**上の層に HTTP の語彙を持ち込まないため**」に存在すると書いてあるのに、
**口の分け方の理由が libs の実装事情**になっている。契約が「なぜ2つあるか」を自分の言葉で
説明できていない。

`accept` にすればこの段落は `backlogGateway.ts` へ移る。あちらは既に `client` / `bytesClient` の
2本を持っている（`backlogGateway.ts:45-53`）ので、**`send` が `request.accept` で選ぶだけ**。
二重性はモジュールの中に閉じ、契約側にはドメインの事実だけが残る。

**原則1 は無傷。** `accept` も input 段が組み立てるので、LLM が指定する口は無い（`method` と同じ）。

#### ただし `accept` 化は 根A を直さない

口を1つにしても、**`download` 分岐から `gateway.send` を素で呼ぶことは依然できる。**
統一が消すのは「新しい口が生えて再発する」経路であって、「保護を貼る」ほうではない。

|                     | 根A を直すか | 再発面を消すか             |
| ------------------- | ------------ | -------------------------- |
| 案3（包んだ口だけ） | **直す**     | 消す（コンパイラが止める） |
| `accept` 化         | **直さない** | 消す（口が増えない）       |

**`PlannedCall.download` も消えない。** この `kind` には2つの理由が乗っている
（①バイト列の輸送 ②`shape: (received: ReceivedAttachment) => unknown` — 受け取り側の I/O を挟む）。
`accept` 化で消えるのは①だけで、共通の末尾に合流できなかった直接の原因は②のほう。

> **段階3の材料**: `PlannedCall.download` の TSDoc（`tools.ts:114-120`）は
> **2つのことを主張している**として扱うこと。

#### 戻り値の表し方で規約との相性が変わる（未検証）

「型が緩む」を理由に退けるかは、**表し方を3つ数えてから決めてほしい。**

| 表し方                 | 呼び出し側       | 実装側                                                           | 規約との関係                  |
| ---------------------- | ---------------- | ---------------------------------------------------------------- | ----------------------------- |
| 条件型 `ResponseOf<R>` | narrowing 不要   | **`as` が要る**（条件型は実装側で検査できない）                  | §4.1 の原則禁止に当たる       |
| オーバーロード         | narrowing 不要   | **`as` が要る**（実装シグネチャが2つ目の戻り値型に代入できない） | 同上。§4.7 の枠に入るかは微妙 |
| **判別子つき union**   | narrowing が要る | **`as` 不要**                                                    | **§4.5 が指定している形**     |

コストは `masters.ts` に集中する。`gateway.send` の呼び出しは本体で **10箇所**（確認）—
`masters.ts:218`・`:267-271`・`:313-315` の**9件が全部 json 固定**、
残り1件が `tools.ts:1943`。`sendBytes` は `tools.ts:1995` の1件。

ただし `masters.ts` は各応答を直後に検証しており（`Array.isArray` /
`toNameToId(value: unknown, …)`）、**受け口が既に `unknown`**。domain 側に
`unwrapJson(response, where)` を1つ置けば既存の検証に畳める。
**これは応答側のアクセサであって口ではない**ので、原則1 には触らない。
`tests/gateway.test.ts` の `.send(` 9箇所も動く。

#### 順序の提案

**案3 を先、`accept` 化は後の巡。** 理由は2つ。

- **案3 は捨て石にならない。** 後で口を1つにすると、包む対象が2メソッドから1メソッドに
  減るだけで、包む構造は残る
- 補遺が「1巡の修正数を絞る」と定めている。根A・B・C と同じ巡に gateway の契約変更を混ぜると
  **どの変更がどの指摘に対応したか追えなくなる**（アンチパターンに名指しされている形）。
  操作としても「足す」+「狭める」で危険度が最上位

`accept` 化をやるなら、**根A の修正とは別の巡・別の commit** にしてほしい。
これは指摘への対応ではなく、**指摘が示した構造への手当て**なので性質が違う。

### DESIGN.md に足すべき1文

直すだけだと同じ穴が残る。応答側の不変条件が**文書に無いこと**が今回の原因なので、
§2 原則1 に送信側と対になる形で置いてほしい。

> 送信側は口を1つに絞って守る。**応答側は、tool 層が包んだ口しか持たないことで守る。**

## 2. 根C — `record()` が try の内側にあるのは意図的。ただしシンクが投げる場合を考えていない

### 当時の意図（コード由来）

### fail-closed は起動時にしか書いていない（確認）

`server.ts:100-102`:

> ファイルに書けなければここで落ちる。監査に寄りかかった設計が監査なしで動くのは、

### 異議 — L1-2 は L1-3 の純粋な下流ではない（確認）

ノートは「**`serve` まで例外が届く経路は `withAudit` の再送出しかない**」と書いている。

**ただし `serve` は `handleMessage` の外でも投げうる。**

```ts
// stdio.ts:59-61
const response = await handleMessage(message, handlers, serverInfo);
if (response !== null) {

つまり **L1-2（誤った文言と、ループごと死ぬこと）は L1-3 と独立に発火しうる。**

「L1-3 を直せば L1-2 は起きない」と読むと**取りこぼす**。順序の結論は変わらない。

## 9. L4-5 — `config.ts:128` の保険（2026-09-07）

**ノートが無い段階で、独立に書いたもの。** 台帳は重要度 L・根F に分類している。
**結論は却下**だが、**却下したことを記録に残す形**で1行だけ足してほしい。

### 「未テスト」ではなく「到達不能」（確認）

if (apiKey.startsWith(CIPHERTEXT_PREFIX)) {

}
```

**dotenvx が正常なら通らない分岐。** カバレッジ計測は「まだ書いていない」と
「意図的に到達しない防御コード」を区別できないので、L4 は機械的に拾っている。

### 保険が守っている契約は、すでに実ライブラリで固定されている（確認）

`tests/apiKey.test.ts:89`:

```ts
it('別の鍵ペアでは送出する（黙って暗号文を返さない）', async () => {
  const other = await seal(otherRoot, 'different-value');
  assert.throws(() => loadConfig(envFor(sealed.env, other.keys)), ConfigError);

```

**モックではない。** `@dotenvx/dotenvx` の `set` で実ファイルを暗号化し、鍵を取り違えて
`loadConfig` を通している。ファイル冒頭が理由も書いている。

> ここだけはモックにしない。守りたい性質が「**ライブラリがどう振る舞うか**」に乗っており、
> しかも上流のテストがその組み合わせを直接カバーしていないため。

**「復号失敗が捕まるか分からない」というリスクは、すでに埋まっている。**

### 到達させると、API キーの経路に差し替え口が増える

`ConfigOverrides.resolveApiKey` は `decryptApiKey` を**丸ごと**差し替えるので、保険を通れない

**それは払いたくない代償。** `ConfigOverrides` の TSDoc 自身がこう書いている。

> env からは触れないので、**設定として危険な値を表現できるようにはならない**

**API キーの経路は、口を増やす場所として最も筋が悪い。**

偽の `loadEnvFile` に `'encrypted:...'` を返させれば `if` が動くことは示せるが、
**それは目で読めば分かること**。証明されないのは「dotenvx が実際にそう返しうるか」で、
そちらは上のテストが担っている。

**カバレッジの1行のために、証明力ゼロのテストと危険な差し替え口を買う**形になる。

### 保険は消さない（役割が違う）

一度「契約テストがあるなら冗長では」と考えたが、**走る場所が違った**。

|                               | いつ・どこで走るか                    |
| ----------------------------- | ------------------------------------- |
| `apiKey.test.ts` の契約テスト | **開発環境**で `npm run check` のとき |
| `config.ts:128` の保険        | **利用者の環境**で、毎回の起動時      |

dotenvx が回帰すれば契約テストは赤くなるが、**それは手元でテストを回したときの話**。

**コードは変えない。** 現状のコメントは「保険」であることは書いているが、
**なぜテストしないか**が書いていない。だから次にカバレッジを測った人が同じ指摘を再生産する。

`config.ts:127` あたりに:

> **この分岐は意図的に未到達。** 到達させるには復号の差し替え口が要り、それは原則1 に逆行する。
> 守りたい契約（復号失敗で送出する）は `tests/apiKey.test.ts` が**実ライブラリで**固定している。
> この保険が居るのは、テストが走らない利用者の環境のため。

台帳は L4-3・L4-5 を根F（エラー経路のテスト欠損）にまとめているが、**性質が違う。**

|                                 | 第三者の名前が入る形                | 囲み | L3-5 の注意書き                    |
| ------------------------------- | ----------------------------------- | ---- | ---------------------------------- |
| **一覧の `name`**（T-2 の対象） | JSON の文字列値。**エスケープ済み** | 無し | **付く**（他の項目が囲まれている） |
| **`findAttachment` の失敗**     | **素のテキスト。改行が生きる**      | 無し | **付かない**                       |

`withUntrustedNotice`（`tools.ts:2566`）は「応答に `<untrusted source=` が含まれるか」で判定する。
**エラー応答には囲みが1つも無いので、注意書きも付かない。**
**囲みも注意書きも無い、素の第三者テキストが出る唯一の経路。**

**そして簡単に踏める** — LLM がファイル名を1文字間違えるだけ。
攻撃者は似た名前のファイルを2つ置けば誘発できる。

### Wiki 側は当たらない（台帳の「同じ判断」は成り立たない）

台帳は「同じ判断が `list_wiki_pages` のページ名にも掛かっている」と書いているが、

throw new Error(`Wiki ページ「${name}」が見つかりません`);

`findWikiId` が載せる `name` は **LLM 自身が渡した引数**で、第三者由来ではない。候補も列挙しない。

根B で表示名を「第三者が書ける」に分類し直したのに、**この経路は囲みの外**。

### 意見

**1. 一覧の `name` は囲まない（現状維持）。**
囲みは DESIGN.md §8 が「緩和であって防御ではない。**対策済みとして数えない**」と宣言しているもの。
**数えないものを付けるために、識別子として使えるという機能上の性質を壊す**のは割に合わない。
しかも構造的なリスクは JSON エンコードが既に潰している。
`tools.ts` のコメント（「囲むと識別子として使えない」）は**正しい判断**。

**2. 直すべきはエラー経路。** これは T-2（トレードオフ）ではなく、**根A と同じ形の欠陥** —
保護が正常系の経路にだけ貼られていて、別の経路が迂回している。
**`callTool` の catch は、こちらが書いた文言と下から来た文言を区別していない。**
`guardGateway` が gateway の失敗を囲むようにしたのと同じことが要る。

**3. 具体案（未検証・段階3 を通していない）。** 候補の列挙**だけ**を囲む。

```ts
throw new Error(
  `添付「${name}」が見つかりません（この課題にあるのは ${wrapUntrusted(available.join(' / '), {...})}）`,
);
```

**識別子としての性質は損なわれない** — 囲まれるのは候補の一覧であって、
LLM が次に渡す `file` 引数そのものではない。役割が別なので両立する。

ただし波及は洗っていない。少なくとも:

- `findAttachment` は `tool/` 層なので `wrapUntrusted` を呼べる。
  **`lookupName` は `domain/` 層で、§4 の語彙表では `untrusted` を知ってはいけない**
  （根A で案2 を却下したのと同じ制約）。**同じ手が使えない**
- `MasterDataError` を `tool/` 層で捕まえて包み直す形になるが、それは `guardGateway` と同じ構造。
  **seam の置き場所が論点になる**
