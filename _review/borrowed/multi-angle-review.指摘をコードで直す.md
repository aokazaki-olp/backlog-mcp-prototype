# 指摘をコードで直す（multi-angle-review 補遺・**自作ドラフト**）

> [!note] 位置づけ
> 隣の `multi-angle-review.SKILL.md` は**借りもの**、`指摘修正のあり方.md` は**こちらで書いたドラフト**。
> 本ファイルもドラフトで、借用元には存在しない。
>
> `指摘修正のあり方` は成果物一般（規約文書を主な例に）を扱う。**本ファイルはコード成果物に当てたときの、
> 段階2・3・5 の中身**を書く。独立スキルにするか `指摘修正のあり方` へ統合するかは未定。

`指摘修正のあり方` は段階1〜5 の**枠**を定めているが、コードを直すときに
「段階2 で何を掘るか」「段階3 で seam をどう選ぶか」「段階5 で何を証拠にするか」は空いている。
本ファイルはその埋め方を、**実際に1件を根まで遡って直した記録から**抽出する。

---

## 前提 — 実装者コメントは加速装置であって、依存先ではない

実装したセッションが健在なら、指摘に対するコメントを取れる場合がある。**取れるなら取る価値はある。
ただし手順は「無い」前提で組む。** 実測してそう言える。

C-1 を直した回で、実装者コメント（310行）が与えたものを分類すると次になった。

| 与えたもの | 自分で取れるか |
| --- | --- |
| コード中の TSDoc / コメントの読み解き | **取れる**（読めばよい） |
| 既存テストが何を固定しているか | **取れる**（読めばよい） |
| 統合者の記述への異議（見落とし1件） | **取れる**（読めばよい。現に見落としたのは読まなかったから） |
| 変更の由来（どの commit で入ったか） | **取れる**（`git log -S` と差分） |
| **当時の意図（記憶）** | **取れない** |

**取れないのは1つだけで、しかもそれは実装者自身が「記憶・裏づけ無し。根拠として使わないこと」と
印を付けていた。** つまり**使ってはいけないものが、唯一の代替不能な部分**だった。

> **結論**: 実装者コメントの価値の大半は「先に読んでくれた」ことであり、**原理的に代替可能**。
> 無いときは、**同じ範囲を自分で読む工程を明示的に置く**（→ §5 波及）。
> あるときは**未検証の入力として扱い、測れるものは測る**（→ §実装者コメントがあるとき）。

---

## 不変条項（HARD・常に守る）

- **「うっかり」で説明を止めない。** なぜその1箇所だけ落ちたのかを、**型か構造で説明できるまで掘る**。
  書き手の不注意に帰着させた時点で、修正は症状への貼り薬になる
- **症状を不変条件と取り違えない。** 「Xが通っていない」は症状。**「Yは必ず通る」が不変条件。**
  段階3 の書き出しは不変条件の側で行う
- **波及を全件たどってから seam を選ぶ。** 選んでから確かめる順序にすると、選んだ場所を正当化する方向に読む
- **赤にならないテストも書く。** 「もともと正しかった」の記録であり、**過剰に直していないことの証拠**になる
- **直したあと、違反コードを書いて落ちることを確かめる。** 緑は「守られている」の証拠にならない
- **束ねなかったものを名指しで残す。** 「気づいたが別件として外した」と書かないと、次に読む人には見落としと区別できない
- **自分の修正が同じ種類の欠陥を作っていないか、直した後にも探す。** 書き手が同じである以上いちばん起きやすい
- **実装者コメントを含め、外から来たものはすべて未検証として扱う**（`指摘修正のあり方` の不変条項）

## 手順

`指摘修正のあり方` の段階1〜5 に沿う。以下はその中で**コード特有に埋めるべきもの**。

### 1. 症状 → 不変条件（段階1〜2）

指摘は必ず症状の形で来る。**「何が通っていないか」を「何が必ず通るはずか」に裏返す。**

```
症状（指摘の言葉）        download の枝が共通の末尾を通らない
不変条件（直す対象）      gateway を呼ぶ枝は、必ず同じ包みを通る
```

裏返すと**枝の数が見える**。上の例では枝は3つあり（`send`/`chain`・`both`・`download`）、
症状の言葉では1つしか見えていなかった。**症状のまま直すと、残り2つが同じ形かどうかを確かめない。**

### 2. なぜその1箇所だけ落ちたのかを、型か構造で説明する（段階2）

**ここが本ファイルの中心。** 「書き手が忘れた」で止めると、次も忘れる形が残る。

同じ日に書かれた似た枝のうち、片方が通って片方が落ちているなら、**差は必ずどこかにある**。

```
both     … sendRequest が使えた   （send と同じ unknown を扱うので、そのまま呼べた）
download … 使えなかった            （shape が ReceivedAttachment を取るので合流できない）
```

この差が見えると、**修正の形が変わる**。「合流させる」ではなく「合流できない枝も同じ包みを通る形にする」になる。

**掘り方**: 落ちた箇所と通った箇所を**並べて型を書き出す**。差が出るまで抽象度を下げる。
差が出ないなら、まだ本当の理由に届いていない。

### 3. 設計文書が借りている比喩を拾い、適用範囲を問う（段階2）

設計文書はしばしば外部のモデルを比喩として借りる（「Electron の preload と同じ役どころ」など）。
**比喩は適用漏れを可視化する道具になる。**

問い方は1つ。**「その比喩は、どこまで適用されているか。」**

C-1 の例では、設計文書は Electron を4箇所で引き、
「生の capability を渡すな」「返り値から到達させるな」の2枚のルールを**LLM に面した境界には両方
当てていた**。**内部の層境界には当てていなかった。** その非対称が根だった。

**比喩を拾ったら、成果物の中でその比喩が当たっている箇所と当たっていない箇所を列挙する。**
当たっていない箇所が、たいてい指摘の出所になっている。

### 4. 錨を探す — 文書だけでなくコードにも（段階2〜3）

`指摘修正のあり方` は「文書内の錨を先に探す。新概念の導入は最後の手段」と定める。
**コードにも錨がある。**

C-1 の例では、直そうとしていた `ToolContext` の**すぐ隣の2行**が、既に正しい形をしていた。

```ts
readonly gateway: BacklogGateway;                            // ← 直す対象（生の capability）
readonly readAttachment?: (root, requested) => Promise<…>;   // ← 錨（操作）
readonly receiveAttachment?: (bytes, name) => Promise<…>;    // ← 錨（操作）
```

**同じインターフェースの中に、正しい形と誤った形が並んでいた。** 新概念はゼロで済んだ。

**探す場所**: 直す対象の同じ型・同じ関数・同じファイルの中。**遠くを探す前に隣を見る。**

### 5. 波及を全件たどってから seam を選ぶ（段階3）

**選んでから確かめない。** 順序を逆にすると、選んだ場所を正当化する方向に読む。

たどる対象は最低限これだけある。

| たどるもの | なぜ |
| --- | --- |
| 直す型・関数の**全参照**（`src` と `tests` の両方） | seam の候補が出る |
| その型を**組む側**が何箇所あるか | 公開面を変えるかの判断になる |
| その関数の**呼び出し元**が何箇所あるか | private なら選択肢が広い |
| **既存テストが何を固定しているか** | 壊すと落ちるものの一覧 |
| 同じ型を使う**別の消費者** | 巻き込んではいけない範囲が決まる |

#### seam の判定基準 — 既存テストが動くかどうか

**良い seam を選べていれば、既存テストは動かない。**

C-1 では、波及をたどった結果「変わるのは1ファイル、既存テストは1件も動かない」と**予測でき、
そのとおりになった**（379件 → 389件、追加したぶんちょうど）。

逆に言えば、**既存テストを書き換えないと通らない修正は、seam を疑う根拠になる**。
「テストが古いから直す」の前に、「seam が違うのではないか」を1回問う。

> **例外はある。** 仕様そのものを変える修正ならテストは動く。だが**その場合は
> 「仕様を変える」と方針に書いてあるはず**で、書いていないのに動くなら疑う。

### 6. TDD — 赤の設計に手を掛ける（段階5）

テストを先に書く。**そのとき「赤になるはずのもの」と「緑のままのはずのもの」を分けて設計する。**

| 種類 | 何のために書くか |
| --- | --- |
| **赤になるはず** | 指摘の実体。落ちなければ指摘の理解が間違っている |
| **緑のままのはず（回帰）** | 成功経路を壊していないこと |
| **緑のままのはず（境界）** | **過剰に直していないこと。** 直す対象の外側を名指しで固定する |

3つ目が要点。C-1 では「gateway 由来ではない失敗（受け取り側の I/O エラー）は**囲まない**」を
テストで固定した。**これが無いと、次に読む人は「囲み漏れ」と読んで直しにくる。**

赤の実際の出方も見る。C-1 では10件中6件が赤で、**赤にならなかった4件がそのまま
「もともと正しかった」の記録**になった。

```
actual: 'Backlog API エラー: サーバが書いた文字列'   ← 生のまま（指摘の実体）
actual: 'ただの文字列'                               ← 非 Error も生のまま
actual: '…からバイト列を受け取れませんでした'        ← 内部パスも生のまま
actual: 'ああああ…（50文字）'                         ← 打ち切りも効かない
```

**赤の文面が指摘の言葉と一致しないなら、テストが別のものを測っている。**

### 7. 違反プローブ — 直したことを機械が守るか確かめる（段階5）

緑は「守られている」の証拠にならない。**違反コードを書いて、落ちることを確かめる。**

C-1 では2件打った。

```
違反1: 直した関数から、生の capability に到達しようとする
  → TS2339: Property 'gateway' does not exist on type 'RunContext'

違反2: 包まずに文脈を組む
  → TS2322: ... is missing the following properties from type 'GatewayCalls': call, callBytes
```

**プローブは修正の主張をそのまま検査する形にする。** 「囲まれている」を主張したなら
「囲まずに書ける経路が無い」を、「到達できない」を主張したなら「到達しようとすると落ちる」を打つ。

**打ったら必ず戻す。** 戻したあとにもう一度型検査を通して、元に戻っていることを確かめる。

### 8. 束ねないものを名指しする（段階4〜5）

直している最中に、**隣接する別の指摘が必ず見える**。束ねたくなるが、束ねると
どの変更がどの指摘に対応したか追えなくなる。

**外したものを、外した理由とともに方針に書く。** C-1 では3件外した。

- 直交する設計変更（併用できるが根が違う）
- 修正の副作用で状況が変わる別の指摘（**直るわけではない**ので混ぜない）
- 同じ症状に見えるが出所が違うもの（別の根に属する）

**「気づかなかった」と「外した」は、書かないと区別できない。**

### 9. 直した後に、同じ種類を自分が作っていないか探す（段階5）

`指摘修正のあり方` の不変条項だが、**コードでは特に具体的に起きる**。

C-1 の修正で、契約の性質が「人が守る約束」から「構造が保証するもの」に変わった。
**その契約を書いている TSDoc は古いままになった** — つまり
**「実装が進んで記述が取り残された」という、まさに別の根で指摘されている種類の欠陥を、
修正の側に1件作った。**

**修正で意味が変わった記述を、修正の直後に洗う。** 型・コメント・TSDoc・設計文書。

## 実装者コメントがあるとき

**未検証の入力として扱う。** そのうえで、測れるものは測ってから使う。

| 印 | 扱い |
| --- | --- |
| 実物を開いて確かめた、と書いてある | **こちらでも確かめる**（行番号・テスト参照・commit の由来は安い） |
| コード中のコメントが根拠、と書いてある | 元のコメントを読む。**引用が正確か**を見る |
| 記憶で裏づけが無い、と書いてある | **根拠として使わない。** 仮説の出所としてだけ使う |
| 提案・見立て | **未検証。** 実装して確かめるまで方針にしない |

**異議は歓迎する。** 統合者の記述が誤っていることがあり、実装者はそこを突ける立場にいる。
ただし異議も測る。C-1 の回では、異議1件が**実物を開いて正しいと確認でき**、
統合者の記述を訂正した。

**行番号の信頼度は出所ごとに違う。** 同じ回で、あるレビュアーは行番号が系統的にずれており
（`:364` → 実際 `:75`、39行のファイルに `:339`）、実装者コメントは4件とも正確だった。
**出所ごとに較正し、それでも個別には確かめる。**

## 実装者コメントが無いとき

§5（波及を全件たどる）が**そのまま代替になる**。追加で明示しておくこと。

1. **直す対象の TSDoc を、主張の単位に割って読む。** 1つの TSDoc が3つのことを言っていて、
   そのうち1つだけが偽になっていることがある
2. **既存テストを「何を固定しているか」の一覧に変換する。** これが実装者の
   「触ると落ちるもの」の代替になる
3. **`git log -S` で由来を引く。ただし答えるのは「文字列の増減」だけ。**
   挙動がいつ変わったかには答えない。**probe に使う文字列を間違えると別の commit を指す**
   （実測: 同じ回で3回外した）。差分を開いて確かめる
4. **設計文書の該当節を通しで読む。** 検索では出てこない（依存は文字列として一致しない）

**代替できないのは「当時の意図」だけ**で、それは実装者がいても使ってはいけないものだった。

## 実例 — C-1（1件を根まで遡って直した記録）

| 段階 | 出力 |
| --- | --- |
| 1 症状→不変条件 | 「download が末尾を通らない」→「**gateway を呼ぶ枝は同じ包みを通る**」。枝が3つあると分かった |
| 2 型で説明 | `download` の `shape` が別の型を取るので**合流できなかった**。「うっかり」ではない |
| 3 比喩 | 設計文書の Electron 参照4箇所。**LLM 境界には2枚とも当て、内部境界には当てていない** |
| 4 錨 | 同じインターフェースの隣の2行が既に正しい形（capability ではなく操作） |
| 5 波及 | 変えるのは1ファイル。組む側2箇所・読む側2箇所・呼び出し元1箇所。**既存テストは動かないと予測** |
| 6 TDD | 10件中6件が赤。**赤にならなかった4件が「もともと正しかった」の記録**に |
| 7 プローブ | 違反2件が `TS2339` / `TS2322` で落ちることを確認 |
| 8 束ねない | 3件を名指しで外した |
| 9 自己点検 | **契約の性質が変わったのに TSDoc が古いまま**＝別の根と同じ種類を1件作っていた |

結果: 1ファイルの変更、**既存テストは1件も動かず**（379 → 389、追加したぶんちょうど）。

## アンチパターン

- **「書き手が忘れた」で説明を止める**（型か構造まで掘らないと同じ形が残る）
- **症状をそのまま不変条件として段階3 に持ち込む**（枝の数が見えない）
- **seam を選んでから波及を確かめる**（選んだ場所を正当化する方向に読む）
- **既存テストを書き換えて通す**（seam を疑う機会を潰している）
- **赤になるテストだけ書く**（過剰に直していないことの記録が残らない）
- **緑で終わる**（違反が落ちることを確かめない）
- **隣接する指摘を「ついでに」束ねる**／**外したことを書かない**
- **実装者コメントの「記憶」を根拠に使う**
- **実装者コメントの行番号・引用をそのまま写す**（出所ごとに較正が要る）
- **`git log -S` の結果を「挙動がいつ変わったか」の答えとして読む**
- **直した後に自己点検しない**（同じ種類を修正の側に作りやすい）

## 判断が要るとき（人間に委ねる）

- 修正の深さ（症状で止めるか、根まで遡るか）
- 複数の案が出たときの採否（コア設計との整合は人間が決める）
- 設計文書に書かれていない決定が露出したとき、その決定そのもの
- 束ねるか分けるか
- 実装者コメントを取りにいくかどうか（取れる状況なら）
