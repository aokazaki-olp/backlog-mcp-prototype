# multi-angle-review スキル

## 目的と中核概念（triangulation）

成果物を、**複数の独立した視点を突き合わせて収束させる**手法でレビューする。研究法・QA の **triangulation** ── 単一視点の盲点を別視点の交差で埋め、視点間の一致を信頼の信号として扱う ── を AI レビューに適用したもの。

**核心の立場**: 品質はレビュアーの数でなく、**統合(consolidation)の判断**で決まる。並列レビュアー=recall(広く候補)、統合者=precision(本物に絞る)。ここを取り違えて「増やせば・回し続ければ良くなる」と思うと、ノイズとトレッドミルに溺れる。

**この手法の正直な限界（必読）**: 本物の triangulation は *手法・データ源が違う* ことで独立を得る。だが AI レビューの「独立」は既定では **手続き的独立**(互いの結論を見せない)に留まり、実体は **同一モデルにプロンプト差分で同一成果物を読ませている**ことが多い。モデル層の盲点は全視点で共有され、**instrument は独立でない**。したがって「一致=高信頼」は近似であり、**共有バイアスによる偽収束は残る**（→ §偽収束）。真の独立に近づける手段 ── **異モデルの併用 / 各視点に外部の真実(公式 docs・参照実装・実行環境)を必ず当てる** ── を独立性の中核として扱う。

構成は **不変条項(HARD)/レビューループ(MODEL=地図)/判断(人間)** の3層 + 横断節(統合・台帳)（[[git-workflow]] と同じ層思想）。

---

## 不変条項（HARD・常に守る）

- **レビュアーの指摘を生で適用しない。** 必ず統合を通す(ノイズ・過剰設計・幻覚が混じる前提)。
- **指摘を自動適用しない。全件を推奨付きで提示し、人間が action を決めてから実行する**(過去の REVIEW.md 運用に倣う。「直すか」の決定自体が人間の判断領域)。**役割固定: AI は統合ドラフト(層割り当て+推奨)を作り、人間が最終 action を決める。** 各指摘に推奨(**修正推奨 / 保留 / 却下**、[[git-workflow]] の「判断が要るとき」と同じ層思想)。※「自明なものは適用してよい」と人間が明示委任したスコープのみ自動適用(既定でしない)。
- **接地 > 自信。** docs/repo/build/実行結果で裏取りしてから採否。「〜のはず」や実在しない参照は幻覚を疑い実物確認。**特に複数視点が一致した指摘こそ接地で裏取りする**(一致は偽収束でも起きるため)。
- **停止条件を先に決める。** 収束 = 直近巡の新規指摘が全て〈cosmetic〉かつ〈単発 lens〉かつ〈接地の裏取りなし〉のとき。**単発でも接地済みなら actionable として少なくとも1巡は扱う**(深い指摘は単発 lens から出る)。**上限巡に達しても未収束なら、残指摘を先送りとして台帳化して停止する**(トレッドミル防止の安全弁)。
- **台帳に残す。** 却下理由・先送りトリガー・状態を記録し、再レビューで閉じた指摘を蒸し返さない（→ §台帳）。
- **stakes に見合うときだけ回す**(規範としての制約はここ。個別成果物の是非は §判断)。
- **承認者が居ない実行(自律・スケジュール等)では apply せず、提示+台帳化して停止(持ち越し)する。**

## レビューループ（MODEL・地図）

1. **視点(lens)を選ぶ。** 相関しない3軸が定石: **〈正しさ〉〈使う側の体験〉〈内部整合・網羅〉**。対象特有の失敗様式が別にあれば1軸を差し替える。**各視点が別々の失敗モードを担当し指摘領域が重ならないか(直交性)を確認**(相関した視点の一致は偽収束を増幅する)。数は対象の失敗モード数に応じ概ね3前後(経験則)。
   - 例: コード=正確性/可読性/整合性 ・ スキル=技術的正しさ/従えるか/内部整合 ・ scaffold=公式準拠/ツールチェーン/拡張性
2. **並列に独立レビュー。** 視点ごとに独立に走らせ、**互いの結論を見せない**(手続き的独立)。**可能なら各視点に外部の真実(docs・参照実装・実行環境)を当て、異モデルも併用する**(instrument 独立=真の独立の中核)。各視点に**自ドメインで確認した項目を最小限報告**させ、空振り(recall 欠損)を可視化する。
3. **統合(consolidation)→ 推奨提示。** 全指摘を層(修正推奨/保留/却下)に割り当て、ランク付き推奨集合として提示(複数一致は優先度を上げるが §偽収束 の対象)。ノイズ・過剰設計は理由付きで却下し台帳へ。**適用は人間承認後(自動 apply しない)。**
   - **不一致(対立指摘)の扱い**: 視点が対立(A「Xせよ」/ B「Xするな」)したら、却下対象でなく**トレードオフの所在を示す一次信号**。多数決で潰さず、**AI は接地とドメイン較正で裁定案(推奨)を提示**し、所在と根拠を台帳に残す。**最終決着は人間**(§判断)。
4. **再レビュー → 収束。** 承認済み修正を適用後、**同じレビュアーを文脈保持で継続**(前巡指摘の解消と二次被害を検証)。**文脈継続できない環境の縮退手順: 各視点へ〈前巡で自分が出した指摘＋その解消状況〉を注入して擬似継続する(他視点由来の判断は注入しない=独立性の担保)。** 蒸し返し防止のため統合者が閉じた指摘を渡す場合は、独立性への小さな妥協として意図的に受け入れる。停止条件に達するまで反復。

### 偽収束への警戒（correlated bias）

- **一致は偽陽性を減らすが、共有バイアス・偽陰性は減らさない。** 「新規 actionable なし」の収束が、**成果物が健全**なのか**レビュアーが枯渇**しただけなのかを区別せよ(各視点が自ドメインを実際に踏んだ痕跡=手順2の確認報告で判定)。
- 相関した視点の一致は偽収束を増幅する → 直交性(手順1)。
- 任意: **red-team / devil's advocate 視点を1つ常設**して groupthink を割る。

### ドメイン較正

「ゼロ曖昧さ・runbook 化」視点は、機械的領域(決定論 spec)で正・判断領域(流動的規約)で category mismatch。判断領域の地図を過剰に縛らない。

### rigor と cost を stakes で配分

- **基盤・広く複製・変更困難** → 収束まで。**使い捨て・変更が安い** → 軽く or やらない(何にでも収束レビュー=プロセスの Feature-YAGNI 違反。[[git-workflow]] のビジネス射影と同型)。
- 量の目安: 視点は3前後、巡数は stakes 相応。**高 stakes でも上限巡を置き、超えたら先送り台帳化**。並列数×巡数がコスト。

---

## 統合（consolidation）— この手法の核

- **recall→precision**: 生の指摘集合から本物へ絞る。
- **収束を信号にするが過信しない**: 複数一致は優先度を上げて提示。ただし相関視点由来なら §偽収束 を疑い接地で裏取り。
- **バイアスを即座に較正**: 特定視点が一定の偏り(例「もっとコード例を」「全部聞け」)を持つなら、個別でなく**その視点の出力全体を割り引く** = そのレビュアー由来の指摘は**独立の裏取りが取れたものだけ採用候補に残す**。
- **却下を理由付きで確定**(台帳へ。蒸し返し防止の最重要作業)。
- **編集は少なく丁寧に**(1巡の修正数を絞ると自傷 regression が減る)。

## 台帳（ledger）

レビューの system-of-record。サブエージェント方式の弱点(揮発・蒸し返し・横断の抜け)を塞ぐ永続層。**呼称は「台帳」に一本化**(固定ファイル名ではない)。

- **置き場所**: [[obsidian-config]] で解決(purpose=`reviews`)。**`reviews` は obsidian.json に事前定義が要る**(未定義なら vault 相対パスを直接指定、例 `ai/reviews`)。**vault が無くても obsidian-config の vault 未確認モードで平文 Markdown として成立する**(Obsidian 必須ではない)。
- **対象1つに1ノート**。対象は `repo + path + 版` で識別(非 git なら版=日付+内容の識別)。中央集約ゆえ**コードとは非同期**(利点=横断集約 / 欠点=PR から見えない)。
- **ID = 視点接頭辞 + 通し番号**(閉じた指摘を次巡へ渡して蒸し返しを防ぐため、なるべく安定させる)。**AI が追記・人間が curate**(却下/削除/リナンバリングは人間権限)。
- 重要度: H=正確性/データ喪失、M=保守性/整合性、L=cosmetic。
- 最小フォーマット(seam であって feature でない。運用の細部は書かない):

```
## <repo+path> レビュー台帳
### 第N巡（日付・版・視点一覧）
| ID | 重要度 | 概要 | 状態 |
|----|--------|------|------|
| <視点>-1 | H | ... | 要対応 / 修正済 / 却下 / 先送り |

**却下(設計意図)**: <ID> — 理由
**先送り**: <ID> — 発火トリガー
**継続検討**: 横断的な指摘
**収束**: 第N巡で新規 actionable なし ／ or 上限で先送り停止
```

---

## 判断が要るとき（人間に委ねる）

- どの視点を立てるか・いくつ回すか
- いつ収束と宣言し打ち切るか
- どの指摘を採用/却下するか、却下の理由付け、**不一致の最終裁定**
- そもそもこの stakes でループを回す価値があるか
- 台帳の却下・削除・リナンバリング

---

## アンチパターン

- **指摘の無批判適用**（recall を precision と取り違える）
- **AI が「自明」と判断して人間承認なしに修正を適用する**
- **一致を偽収束の可能性ごと過信する / 相関した視点で triangulation を装う**
- **「レビュアーを増やせば・回し続ければ良くなる」**（トレッドミル）
- **自信を接地より信じる**（「〜のはず」や実在しない参照を裏取りせず採用する）
- **何にでも収束レビュー**（stakes に配分せよ）
- **台帳なしで運用 / 却下を記録しない**（蒸し返す）
- **レビュアーに互いの結論を見せる**（独立性が崩れる）

---

## 適用条件・位置づけ

- **まず stakes と単発性を判定**。単発 diff の軽いレビューは組込 `/code-review` に降ろす。**single-lens で不安が残る / stakes が高いなら本手法へ昇格**。
- 本スキルは**実験的で育てる前提**(使って噛まれた所を台帳に残し改訂。このスキルにも rigor-by-stakes を適用)。
- 関連: [[git-workflow]]（層割り当て・ビジネス射影）、[[obsidian-config]]（台帳の置き場所解決）。
