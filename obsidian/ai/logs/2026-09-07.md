## 07:01 — 監査ログに既製品を使えるかを調べ、実機で確かめた

### 事実（きっかけ）

### 事実（npm の実態）

`registry.npmjs.org/-/v1/search` で「audit log」「audit trail」「tamper-evident log」等を引くと2群に割れる。

- **フレームワークのプラグイン**（Loopback / Payload / Strapi / Backstage / AdminForth）— ORM や CMS の

### 事実（実機・Node v24.20.0・`sonic-boom@5.0.1`）

## 08:09 — 根C を段階3〜5 まで通し、監査層を修正

### 事実

**裁定を人間から取った（2件）。**

1. **稼働中に監査が書けなくなったら止める。** ただし「意図した停止」にする
2. **直前の1件には結果をそのまま返し、同じ応答に利用者への告知を1ブロック足す。**
   `isError` には載せない（仕様が `isError` を「モデルが自己修正して**再試行**するための feedback」と
   定義しており、再試行こそ最悪の結果 — Backlog への投稿は済んでいるので二重投稿になる）

裏取りは `docs/reference/mcp/specification/2026-07-28/server/tools.md` §Error Handling。
Server errors はプロトコルエラー側に名指しされ、tool execution error は
「クライアントは LLM に見せる**べき**（SHOULD）」、protocol error は「見せて**よい**（MAY）」。

**実測を3件取った（すべて自分で走らせた。Node v24.18.0）。**

- **L1-1 の再現**: 実装者ノートと同じ結果（`fd=20`, `markerFd=20`）。**`EBADF` は起きず、
  巻き添えの書き込みが監査ログのファイルへ入る**。L1 の報告より1段悪い
- **sonic-boom 5.0.1 の失敗経路**: 構築も `reopen` も**同期送出**。失敗後は古い fd を保持したまま
  書き続ける（`"day06\nafter\n"`）。`uncaughtException` はこの経路では出ない
- **型と実行時が正反対**: `import SonicBoom from 'sonic-boom'` は実行時に動くが型で `new` できない
  （TS2709 / TS2351）。`import { SonicBoom }` は型が通るが実行時に `SyntaxError`。
  両方を満たすのは `import SonicBoomModule` ＋ `import type { SonicBoom }` ＋
  `new SonicBoomModule.SonicBoom(...)` の形だけ（`as` 不要・lint も通る）

**sonic-boom のソースに同種の欠陥を見つけた**（`index.js:527-531`）。`reopen` は `once('ready')` を
**開く前に**登録するので、開けなかったときリスナが残り、次に成功したとき**同じ fd を2回 close する**。
ただし決定的ではなく、失敗時にデータを失わず、`'error'` に `EBADF` が流れる（現行の手書きは
決定的・沈黙・気づけない）。**裁定「止める」を入れると sonic-boom 側の経路は到達不能になる。**

**修正**（`src/` 5ファイル・`tests/` 2ファイル）。

- `AuditSink` の契約に「`write` は投げる」を書いた（型は変えていない）
- `AuditUnwritableError`（`result` と `suppressed` を持つ）と `AUDIT_STOP_NOTICE` を追加
- `withAudit` はシンクの失敗を捕え、**手元の `ToolResult` を載せて**投げる。結果を捨てない
- `serve` は `handleMessage` と `channel.write` を try で包み、**1リクエスト1応答**を守る。
  `RPC_ERROR.INTERNAL`（定義だけあって未参照だった）に初めて使い道が付いた
- `serve` は例外で終わらず `ServeOutcome` を返す。`main.ts` が「起動に失敗しました」と
  「サーバを停止しました」を言い分ける
- `createFileAuditSink` の記述子管理を sonic-boom へ委ね、**時計の注入口**を足した

**結果**: `npm run check` 緑（**403件 pass**。393 → 403 で、増えたのは追加した10件ちょうど）。
`npm run verify:rules` **28/28**。`npm pack` は30ファイル・312 kB で、`dist/mcp/audit.js` に
ベア指定の import が残り、型だけの import は消えている。

**違反プローブを3件打ち、すべて赤になることを確認して戻した。**
①結果を捨てる ②告知を載せない ③応答せずに読み飛ばす。

### 解釈

**3件が同時に落ちていた理由は「うっかり」ではない。この設計には
「稼働中に監査が書けなくなった」という状態が存在しなかった。**
`AuditSink` の型、`multiAuditSink` のコメント（「起動を続けない」）、`@throws {ConfigError}`、
README の「書けなければ起動しない」— すべて**起動時の語彙**で書かれている。
だから4箇所とも書き込みを絶対に失敗しないものとして書かれた。

**`RPC_ERROR.INTERNAL` が定義だけで未参照だったのは、
「1リクエストに必ず1応答」という不変条件が最初から実装されなかった化石。**

**自分の案が、実装者ノートが名指ししている失敗と同じ形だった。**
最初は停止機構を optional の引数で渡す案を出したが、ノート §4 は sonic-boom の `'error'` リスナに
ついて「付け忘れると挙動が変わる。**設定で守るのであって構造ではない**」と書いている。
しかも私はそれを「既存テストが動かないから良い seam だ」と正当化していた。
**例外の型で運ぶ形に変えたら、構造で守れて既存テストも動かない** — 両立した。

**ノートの見立てを1件訂正した。** 「リスナを付ける＝続ける / 付けない＝伝える」は正しくない。
リスナの無い `'error'` は `uncaughtException` になるので、**リスナの有無は
「制御された停止か、既定のクラッシュか」**。裁定が「止める」でもリスナは付けるのが正しい。

### 決定

- **L4-4（`withAudit` の例外経路が未テスト）を根F から根C へ移して閉じた**（人間の承認済み）
- **束ねずに外した**: `server.ts:160` の起動時同型 / `stderrAuditSink` の EPIPE /
  `withAudit.listTools` が何も記録しない（根D で決める）/ DESIGN.md §5 の**理由の書き直し**
  （「監査は消せる口を持たない」を原則として書く案。根E の側）
- **`VERSIONS.md` の「実行時依存 — `got` のみ」は元から偽**（`@dotenvx/dotenvx` と `file-type` が既にある）。
  `sonic-boom` を足して一段偽になったが、**元からあった乖離なので黙って直さず根E へ送った**。
  引き継ぎが申し送っていた「自分の修正が偽にした記述」と「元からあった乖離」を分ける語彙が、
  ここで初めて実際に効いた
- **`'error'` リスナは一度失敗したら以後も失敗させる。** ローテーション成功後の close 失敗のような
  実害の無い失敗でも止まりうるが、fail-closed の側へ倒す（コメントに書いた）
