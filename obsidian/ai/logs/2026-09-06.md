## 04:21 — Backlog が Wiki 機能の廃止を予定していることが判明した

`list_wiki_pages` が実スペースで失敗した。

```

```

当初「試用スペースだから」と推測したが誤りで、公式ブログ（https://backlog.com/ja/blog/backlog-update-wiki-end-of-support-new-spaces/ ・2026-09-06 取得）に理由があった。原文。

> Backlogでは、ナレッジ管理機能をドキュメント機能へ統合していく長期的な方針のもと、将来的にはWiki機能の廃止を予定しております。

> APIをご利用のシステム連携につきましては、Wiki機能の廃止に伴い順次影響が発生する見込みです。

- 2025年12月 ドキュメント機能が正式リリース、Wiki からの移行機能も提供
- **2026年7月14日** 新規スペースに Wiki を提供しない。既存スペースの新規プロジェクトも既定オフ

## 16:20 — 添付のダウンロードを入れた（`11c83d0`）

網羅検証ノート §2.2「添付ファイルをダウンロードできない ⭐」の保留を解いた。ツールは 22 → 24 本、テスト 373 件で緑。

### 決めたこと — テキストは LLM、それ以外はディスク

囲み（`<untrusted>`）は**テキストにしか効かない**。バイト列を LLM のコンテキストへ流すと、このサーバで初めて「囲みの外側にコンテンツが出る」ケースになる。そこは開けない、と決めた。

| 中身 | 返すもの |
| --- | --- |
| テキスト系 | `<untrusted>` で囲んだ本文。ディスクを触らない |
| それ以外 | `BACKLOG_DOWNLOADS_DIR` へ保存してパスを返す |

Desktop でバイナリを AI に読ませたいなら、**人がダウンロードフォルダから選んで上げ直す**。囲みを掛けられない問題を人間の承認で置き換えている。インジェクションが消えるわけではない（上げ直せばコンテキストには入る）が、防いでいるのは**自動で引き込まれること**のほう。

### 前提が覆った — 借り物のクライアントがバイナリを落としていた

`BacklogApiClient` は `responseHandler: response => response.body` を焼き込んでいる。**バイナリの応答では `body` が `null`** で、生バイトは `bytes` にしか入らない。`src/libs/` はローカル編集できない（`AGENTS.md`）。

公開されている `extend`（Transport のデコレータ）で `bytes` を `body` に移す別クライアントを立て、`sendBytes` に割り当てた。上流に手を入れず、`libs/` を知ってよい層（`backlogGateway.ts`）に閉じている。

### 保存側は読み取り側より厳しくする

人が開く場所に置くので、保存できるのは `.png` / `.jpg` / `.gif` / `.pdf` だけ。ファイル名は第三者が決めるので、ディレクトリ区切り・`..`・`:`・制御文字・Windows の予約名・末尾のドットと空白を**直さずに弾く**（直すと何が保存されたか予測できなくなる）。上書きせず連番。

`BACKLOG_DOWNLOADS_DIR` に**既定を置かない**。OS 既定のダウンロードフォルダは推測しない — Windows の既定は移動でき、Linux は XDG でロケール依存になりうる（未確認）。確かめていない値を既定にしない。読み取りルート・監査ログ・設定ファイルと重なっていたら起動しない。

## 17:00 — 添付を「明示しないと有効にならない」に揃えた

ユーザーの問い「upload/download は `can` で個別に指定しないと有効にならないようにしておこうか」から。**狙いには同意したが、置き場所は `can` ではないと判断した。**

### 採らなかった案 — `can` に添付を足す

3つの理由で却下。

- **`can` は単調な階梯であって、フラグの集合ではない。** `read < comment < write` は順序があり上位が下位を含む。添付はこの順序のどこにも乗らない。列挙にすると「`["read","write"]` と `["write"]` の差が曖昧になるから単一値にした」判断に逆行する
- **添付の危険は「機能」に属していて、「プロジェクト」に属していない。** ダウンロードはどのプロジェクトでも第三者が同じ形で仕込める。アップロードで何が出ていくかは `BACKLOG_ATTACHMENTS_ROOT` で決まり、宛先プロジェクトでは変わらない
- **3軸モデルは「プロジェクトに属さない軸」を持てない。** `Set<(projectKey, toolName)>` へ畳む形なので表せない。しかも**アップロードはツールではなく引数**（`file`）

### 見つけた穴 — テキストのダウンロードだけが設定ゼロで開いていた

| | 直す前の既定 | 有効化 |
| --- | --- | --- |
| アップロード | オフ | `BACKLOG_ATTACHMENTS_ROOT` |
| ダウンロード（バイナリ） | オフ | `BACKLOG_DOWNLOADS_DIR` |
| **ダウンロード（テキスト）** | **オン** | **— 設定ゼロ** |

テキストの添付だけが read を許した副作用として黙って付いてきていた。**指摘の直感は当たっていて、場所が違っただけ。**

### やったこと

- `BACKLOG_DOWNLOADS_DIR` を「保存先」から**ダウンロードの鍵**に格上げ。未設定なら `list_issue_attachments` / `get_issue_attachment` を `tools/list` に出さず、`tools/call` でも拒否する（テキストも含めて閉じる）
- `BACKLOG_ATTACHMENTS_ROOT` 未設定なら、6ツールのスキーマから **`file` 引数だけを落とす**（ツールごとは消さない。コメント自体は添付が無くても使える）
