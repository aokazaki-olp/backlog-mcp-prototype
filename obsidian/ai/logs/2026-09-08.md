### 解釈

- **「契約モデル」として切り出せるコードはほとんど無い。** 移植されたのは
  `{ readonly [K in ToolName]: … }` という**1行の型注釈を4箇所に置く作法**であって、
  ライブラリ化できる実体（関数・データ）ではない。汎用化して残るのは型ユーティリティ数十行で、
  同期スクリプト・`SOURCE.md`・版固定のコストのほうが大きい。
- **出せるのは契約の「周辺」**。MCP プロトコル層（`protocol` / `stdio` / `audit`）・
  `shared/` 3本・ポリシーの正規形エンジンは Backlog を知らない。
- **`src/libs/` の枠には置けない。** `eslint.config.js` が `src/tool/**` から `**/libs/**` の
  import を禁止しており、契約は tool 層が必ず import する。加えて `libs/` は lint / typecheck の
  対象外（規約 §8.3）なので、**型が命の契約を検査の外に置く**ことになり本末転倒。
  「自分のコード / 借り物・生成物」の二分法に、**新規約で書かれた共有物**という第三の枠が要る。
- **汎用化の費用は型パラメータではなく利用者向けの語彙**。ポリシーファイルの鍵名（`projects` / `key`）と
  エラーメッセージ（「プロジェクトキー」）が汎用側では「スコープ」に薄まる。
- Rule of Three の観点では消費者が1つなので**今は早い**。DESIGN §10 が `preset` を
  「3回目が出てから」としているのと同じ基準を当てるなら、判断点は2つ目の MCP サーバに着手するとき。
